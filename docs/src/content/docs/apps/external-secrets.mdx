Every deployment secret lives in one 1Password vault. External Secrets Operator (ESO) reads the vault through a 1Password Connect server in the cluster and builds each Kubernetes Secret from it. `cluster.toml` holds no secret: a section is turned on by a flag or a client ID, and its secrets are fields of the section's vault item. This page covers the `[onepassword]` section, how an item and its fields are named, how to add or rotate a secret, how to check the vault, and what happens when 1Password is unreachable. The deployment itself is in Git: `kubernetes/apps/external-secrets/`.

The migration from sops finished on 2026-11-23. The Talos secrets bundle and `talosconfig` are documents in the same vault, and no file in the repo is encrypted.

Each claim names its source. "Template" is a file under `template/config/`. "Rule" is `.claude/rules/apps/external-secrets.md`. "Measured" names its date.

## What it is

The `external-secrets` namespace holds two Flux apps (template, `kubernetes/apps/external-secrets/`):

- `external-secrets`, the operator, from its chart with the CRDs installed by the chart.
- `onepassword-connect`, the Connect server, one replica on an `emptyDir` (rule), plus the `ClusterSecretStore` named `onepassword-connect`. The store reads the one vault that `[onepassword]` names, at `http://onepassword-connect.external-secrets.svc.cluster.local:8080`. The Flux Kustomization reports Ready only when the store does.

Every app that needs a secret has an `ExternalSecret` in its own folder, with `refreshInterval: 1h`. Each one lists its keys in `target.template`, because an extract returns every field of the item (rule).

One `ClusterExternalSecret`, `cluster-secrets`, writes the Secret `cluster-secrets` with the key `SECRET_DOMAIN` into every namespace except `cilium-secrets`, `external-secrets`, `kube-node-lease` and `kube-public`. Flux substitutes `${SECRET_DOMAIN}` from that Secret. Its `creationPolicy` is `Orphan`, so deleting the object never deletes a copy (template, `onepassword-connect/app/clusterexternalsecret.yaml.j2`).

## What `[onepassword]` holds

One field (`cluster.sample.toml`):

- `vault`: the name of the vault the Connect server can read. Letters, digits, `_` and `-` only. It is rendered into the repo, so pick a name you are content to publish. This page writes it `<vault>`.

The field is required. The validator refuses a config without it, with the message "onepassword.vault is required: the domain and every secret are read from it" (`template/scripts/validate.py`).

## How an item and its fields are named

`template/scripts/secret_map.py` is the list of record. Read it for the item and the field before creating either.

- One item per `cluster.toml` section, titled with the section name in hyphens: `[postgres.backup]` is the item `postgres-backup`, `[cilium.hubble]` is `cilium-hubble`, `[pocket_id]` is `pocket-id`.
- The title follows the section, not the app: `unifi` holds the UniFi DNS key, and one `career-ops` item feeds three Secrets (rule).
- A field's label is the name the field had in `cluster.toml`, in upper case: `OIDC_CLIENT_SECRET`, `ENCRYPTION_KEY`, `ACCESS_KEY_ID`.
- A label holds no space, and an item holds no label twice. One such label fails ESO's read of the whole item (`template/scripts/secrets_check.py`).

Items that do not follow from a section field:

| Item | Fields | Needed when |
| --- | --- | --- |
| `cluster` | `SECRET_DOMAIN` | Always |
| `dns` | `TOKEN` | `dns.provider` is `cloudflare` |
| `cloudflare-tunnel` | `ACCOUNT_TAG`, `TUNNEL_SECRET` | `ingress.mode` is `cloudflare-tunnel` |
| `flux` | `WEBHOOK_TOKEN` | `repository.webhook_provider` is set and not `none` |
| `kener` | `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS` | `kener.smtp` is on |
| `ai-workspace-env` | One field per name in `ai_workspace.env_keys` | A name is listed |
| `1password` | `OP_CREDENTIALS_JSON`, `OP_CONNECT_TOKEN` | Always. The Connect server starts from them |

The last row is from `template/config/bootstrap/onepassword.yaml.j2`. The rest are from `secret_map.py`.

## Add a secret

1. Find the section's entries in `secret_map.py`. A new section needs new entries there first.
2. In 1Password, open the vault and create the item by hand, titled as above, with one field per label. No command seeds the vault.
3. Set the section's flag or client ID in `cluster.toml`.
4. Check the vault, then render:

    ```sh
    just template secrets-check
    just configure
    ```

5. Commit and push.

## Rotate a secret

Change the field in 1Password. Nothing in Git changes. The ExternalSecret reads the vault again within the hour and rewrites the Secret, and Reloader restarts the pods that watch that Secret.

Some values need more than the vault change, because the app stored the old value on its first start or reads it only at install. Each app's page says so. Three patterns recur:

- A key that encrypts stored data (`pocket-id` `ENCRYPTION_KEY`, `pegaprox` `DB_KEY`, `ai-kb` `AES_KEY`) must never change, or needs the app's own rotation command first.
- The media keys and the RustFS consumer pairs reach their apps through a Job. Raise `media.keys_revision` or `rustfs.keys_revision` in `cluster.toml` after the vault change, then render and push (`cluster.sample.toml`).
- CLIProxyAPI's `MANAGEMENT_KEY` and `API_KEY` are seeded into the app's config once. See [CLIProxyAPI](/apps/cliproxyapi/).

## Check it

The vault, from the admin machine with the `op` CLI signed in:

```sh
just template secrets-check
```

It reads `cluster.toml` for which fields are needed, reads each item, and prints one line per problem as `<item>/<field>: <problem>`, then the count. The problems are `missing`, `pattern` (the value fails its format), `label has a space`, `duplicate label` and `same as <item>/<field>` for two keys that must differ. It never prints a value (`secrets_check.py`).

The cluster:

```sh
kubectl get clustersecretstore onepassword-connect
kubectl get externalsecret -A
kubectl get clusterexternalsecret cluster-secrets
```

The store and every ExternalSecret report Ready.

## When Connect or 1Password is unreachable

- Secrets that exist stay as they are, and the pods that use them keep running. ESO only fails the refresh and marks the ExternalSecret not Ready. This is ESO's documented behaviour and was not measured on this cluster.
- A Secret that does not exist yet waits, and a new app's pods cannot start until its ExternalSecret syncs.
- `media-shared` has `wait: true`, so the media apps' Kustomizations wait on it while the vault is unreachable (rule).
- The Connect server keeps its cache on an `emptyDir`, so a restarted Connect pod has to reach 1Password before it answers again (inferred from the `emptyDir`; not measured).

## Two guards against losing every Secret

An ExternalSecret owns the Secret it builds, so deleting the ExternalSecret deletes the Secret. Two guards keep one mistake from doing that to all of them:

- The ESO CRDs carry `helm.sh/resource-policy: keep`. Removing the chart does not delete the CRDs, which would delete every ExternalSecret and every Secret one owns (template, `external-secrets/app/helmrelease.yaml.j2`).
- The validator requires `onepassword.vault`. An empty vault would render the whole namespace away, and Flux would prune the operator and the store (`validate.py`; rule).

The two Secrets the Connect server starts from and every copy of `cluster-secrets` are not owned at all: their ExternalSecrets use `creationPolicy: Orphan` (template; measured 2026-11-22, synced with empty `ownerReferences`).

## Bootstrap

ESO cannot build the Secrets that Connect itself needs. `just bootstrap apps` applies them from `bootstrap/onepassword.yaml`, which holds `op://<vault>/<item>/<field>` references and no value, through `op inject` (template, `bootstrap/mod.just`). The file creates three Secrets:

- `onepassword-connect-credentials` and `onepassword-connect-token` in `external-secrets`, from the item `1password`.
- `cluster-secrets` in `flux-system`, from the item `cluster`, because the `flux-system` Kustomizations substitute the domain before ESO runs.

The recipe needs the `op` CLI signed in and internet access to 1Password. It stops with "1Password is unreachable or signed out, bootstrap cannot continue" otherwise. Once ESO is up, two ExternalSecrets refresh the Connect Secrets from the vault.
