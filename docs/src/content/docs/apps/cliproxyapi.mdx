The steps outside the repo that `[cliproxyapi]` in `cluster.toml` needs, in order. CLIProxyAPI is an OpenAI-, Anthropic- and Gemini-compatible proxy that pools subscription logins (Claude, Codex and others) behind one client key. CPA-Manager-Plus is its management UI. The deployment itself is in Git: the `[cliproxyapi]` section and `kubernetes/apps/llms/`. "Measured" below was run in Docker against `eceasy/cli-proxy-api:v8.0.58` and `ghcr.io/seakee/cpa-manager-plus:v1.14.10` on 2026-11-06, under the pods' restrictions (read-only root, every capability dropped, uid 1000), or on the cluster where it says live. It went live as a proof of concept on 2026-11-06.

Using a subscription login through a proxy may breach the provider's terms of service, and the account can be suspended.

## What it holds

Both apps run in the `llms` namespace, which enforces the `restricted` pod security level, and both are on the internal gateway only, with no gateway `SecurityPolicy`:

- The proxy, `cliproxyapi`, at `https://llms.${SECRET_DOMAIN}` on port 8317. Clients send `api_key` as a bearer token.
- The manager, `cpa-manager`, at `https://llms-admin.${SECRET_DOMAIN}` on port 18317. Its admin key is its only login.

Both images set no `USER`, so the pods set uid 1000, and both run on a read-only root (measured). Each has a 1Gi `local-path` volume at `/data`, kept when the claim is deleted, and each volume is the only copy of what it holds:

- The proxy's volume holds `config.yaml`, `auths/` (the provider OAuth token files) and `kv.db`.
- The manager's volume holds `data.key`, `usage.sqlite` and its WAL, a lock file and `usage-imports/`. `data.key` encrypts the management key the manager stores. Losing it makes the stored key unrecoverable.

There is no volume backup, no metrics, and no provider API keys in the config. The provider logins are OAuth logins added in the manager.

## Keys

Generate each value once:

```sh
openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 48; echo               # management_key
openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 48; echo               # api_key
echo "cpamp_$(openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 40)"     # manager_admin_key
```

Each is at least 32 characters. The manager's docs describe the key it generates when none is set as `cpamp_...`, so the example keeps that prefix. Whether a key set by hand needs it is not checked.

## cluster.toml

Section `[cliproxyapi]`: the three values above, set together or not at all. It needs no other section. `just template scaffold cliproxyapi` adds the block in the sample's position with its keys commented.

Then `just configure`, restore the sops files that did not change:

```sh
git checkout -- ':(glob)bootstrap/**/*.sops.*' ':(glob)kubernetes/**/*.sops.*' ':(glob)talos/**/*.sops.*'
```

Commit the rendered `kubernetes/apps/llms/`, then push. `just kube reconcile` makes Flux pull now.

## First start

```sh
kubectl get kustomization -n flux-system cliproxyapi cpa-manager
kubectl get pods -n llms
kubectl logs -n llms deploy/cliproxyapi -c seed-config
kubectl logs -n llms deploy/cliproxyapi
kubectl logs -n llms deploy/cpa-manager
```

Both Kustomizations Ready, both pods Running and Ready. The manager starts after the proxy, because its `wait-for-proxy` init container waits for the proxy's `/healthz`. The `seed-config` log is empty, because `cp` is silent. The proxy log shows no config error, and the manager log shows no connection error to `http://cliproxyapi.llms.svc.cluster.local:8317`.

Git seeds the proxy's config once. `cliproxyapi-secret` holds a whole `config.yaml`, mounted read-only at `/seed`, and the `seed-config` init container copies it to `/data/config.yaml` only when that file is absent. The app rewrites the file at start (it replaces the plaintext management key with its bcrypt hash) and saves every management-API write to it, so a read-only file makes those writes answer 500 (measured). After the first start the manager UI owns the config.

The seed sets values the app needs:

- `server.port: 8317`. Without it the app bound `:0`, and the probe on 8317 killed the pod (measured live, 2026-11-06).
- `trusted-proxies` set to the pod CIDR, because the gateway forwards the client address and the app bans an address after five bad management keys.
- `disable-control-panel: true`, which turns off the bundled panel the app would otherwise download from GitHub. `/management.html` is 404 on the proxy.
- `usage-statistics-enabled: true`, which feeds the manager's usage pages, and `redis-usage-queue-retention-seconds: 3600`, the maximum, so the proxy keeps an hour of usage in memory and a manager restart loses nothing (the default is 60 seconds).
- `routing.cooldown.save-cooldown-status: true`, so a throttled login stays out of rotation across a restart.
- `requests.nonstream-keepalive-interval: 30`, blank lines on long non-streaming answers. The gateway's request timeout is already unlimited, so this guards only its stream idle timeout (inferred, not measured).

Left at the defaults on purpose: round-robin routing with one-hour session affinity (a Claude Code session stays on one login for its prompt cache), per-credential rather than per-model cooling (a Max plan's limits are per account), cloak mode `auto`, no header defaults or device-profile pinning, and request logging, plugins, pprof and commercial mode off. The Antigravity, quota-fallback and multimedia settings do not apply to Claude logins. The proxy refreshes its OAuth tokens every 15 minutes (measured from its start log).

The manager runs with `USAGE_ACCOUNT_ACTIONS_ENABLED=true`, a record-only review queue of revoked or invalid logins. Auto-disable and the quota cooldown worker stay off: auto-disable is never reversed by a worker and needs a re-login, and the cooldown worker reads Codex and xAI signals only. The server Health Inspection covers Codex and xAI only, so its schedule stays disabled.

The image has a Cmd and no Entrypoint, so the HelmRelease sets `command` to the binary and its `--config` flag; `args` alone would replace the binary.

## Sign in and first use

Open `https://llms-admin.${SECRET_DOMAIN}` from the LAN and sign in with `manager_admin_key`. After sign-in the status page shows the collector running.

Add the provider logins in the manager:

1. Add a Claude (Anthropic) OAuth login. The manager returns an authorization URL.
2. Sign in to Claude in the browser tab it opens. The browser then lands on `http://localhost:54545/callback?...` and fails to load. That is expected.
3. Copy the whole URL from the address bar and paste it into the manager's callback field.

Codex takes the same steps, and its failing page is `http://localhost:1455/auth/callback?...`.

Measured 2026-11-07: three Claude accounts were added this way in a row, each in under two minutes. Every one landed as its own `claude-<id>-<account>.json` under `auths/`, the proxy logged `Authentication successful` and picked the file up without a restart, and the manager's Credential Management page showed all three as Available on their plan after Refresh quota. A second account needs a private window, because claude.ai authorizes whichever account that browser is signed in as. Not yet seen: whether the tokens refresh on their own over days.

## Clients

Claude Code, in the user's `~/.claude/settings.json` (never a project's committed `.claude/settings.json`). Claude Code's gateway docs say the base URL carries no `/v1` and `ANTHROPIC_AUTH_TOKEN` goes out as `Authorization: Bearer` (read 2026-11-07):

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://llms.${SECRET_DOMAIN}",
    "ANTHROPIC_AUTH_TOKEN": "<api_key>"
  }
}
```

Codex needs a Codex login in the proxy first (none added yet). Then, from CLIProxyAPI's own Codex page
(read 2026-11-07, not yet tried here), `~/.codex/config.toml`:

```toml
model_provider = "cliproxyapi"

[model_providers.cliproxyapi]
name = "OpenAI"
base_url = "https://llms.${SECRET_DOMAIN}/v1"
http_headers = { "X-Api-Key" = "<api_key>" }
wire_api = "responses"
requires_openai_auth = true
supports_websockets = true
```

`env_key = "<VAR>"` is the official alternative to the literal header, and `wire_api` has only the
value `responses`.

From the LAN, this lists the models of the logins added:

```sh
curl -s -H "Authorization: Bearer <api_key>" https://llms.${SECRET_DOMAIN}/v1/models
```

Measured 2026-11-07 with three Claude logins: the list held nineteen Claude models, and a one-word
request to `claude-haiku-5-5` answered through both `/v1/messages` (Anthropic format) and
`/v1/chat/completions` (OpenAI format), with the request attributed to one account in the
manager's Credential Management page.

## Operations

- Change proxy settings in the manager's Config Panel, which persists and reloads them. An edit to `/data/config.yaml` through `kubectl exec` is not picked up by the file watcher (measured 2026-11-07, with `sed -i` and with an in-place rewrite) until `kubectl rollout restart deploy/cliproxyapi -n llms`. `GET /v0/management/config` with the management key shows the live values.
- A change to the seed in Git reaches a running proxy only if the volume's copy is deleted, because init containers run once per pod and only the `seed-config` init container mounts the seed. Delete the copy and restart, which re-seeds it. Every setting made in the UI is lost; the provider logins under `auths/` stay. Rotating `management_key` or `api_key` needs this re-seed: the manager picks up its new Secret on its own, the proxy's stored hash does not, and the two stop agreeing. Whether the manager accepts a changed management key once it has stored one is not checked.

    ```sh
    kubectl exec -n llms deploy/cliproxyapi -c app -- rm /data/config.yaml
    kubectl rollout restart deploy/cliproxyapi -n llms
    ```

- Run one manager per proxy. Exactly one manager subscribes to a proxy's usage queue, so the manager has one replica. Both Deployments use `Recreate`, one writer per volume.
- The manager's collector picks its transport once, at start. Started while the proxy was down, it fell back to HTTP polling, two `GET /v0/management/usage-queue` a second in the proxy's log. Restarted with the proxy up, it chose `subscribe` (measured live, 2026-11-06). A `wait-for-proxy` init container holds the manager until the proxy's `/healthz` answers. The transport check is under Verify.
- Egress is open. The proxy dials the providers, and at start and every three hours it runs an antigravity version check and fetches the Grok CLI version from npm.
- NetworkPolicies admit the `network` namespace on each app's port, and the proxy also admits the manager's pods on 8317.
- The Config Panel's Source File Editor shows the proxy's config with the client key in plaintext to anyone signed in to the manager, so the admin key is the only wall around that key.
- Log stamps read +08:00. The image bakes `TZ=Asia/Shanghai`, and a `TZ` env did not change them (measured live).
- Not done: no volume backup, so the OAuth tokens and the manager's `data.key` exist only on their volumes.

## Verify

```sh
curl -s -o /dev/null -w '%{http_code}\n' https://llms.${SECRET_DOMAIN}/healthz
curl -s -o /dev/null -w '%{http_code}\n' https://llms.${SECRET_DOMAIN}/v1/models
curl -s -o /dev/null -w '%{http_code}\n' https://llms-admin.${SECRET_DOMAIN}/health
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://llms-admin.${SECRET_DOMAIN}/
```

Measured through the gateway, 2026-11-06: the proxy answers `/healthz` with 200 and `/v1/models` without a key with 401. The manager answers `/health` with 200 and `/` with 307 to `/management.html`. The proxy's `/health` is 404.

The collector's transport, which should read `subscribe` in `collector.transport`:

```sh
kubectl exec -n llms deploy/cpa-manager -- sh -c 'wget -qO- --header "Authorization: Bearer $CPA_MANAGER_ADMIN_KEY" http://127.0.0.1:18317/status'
```

## Updates

Renovate offers both images, pinned by digest, and neither is in the weekend digest automerge, because the proxy's volume holds provider logins. A seed change in an update reaches a running proxy only by the re-seed under Operations, because the running config is the one on the volume. The manager's docs say its HTTP usage queue needs CLIProxyAPI v6.10.8 or later.

## If something breaks

- The proxy HelmRelease stays Ready=False with `MissingRollbackTarget`: every release in a rollout failed its five-minute wait. Once the Deployment is healthy, `flux reconcile helmrelease cliproxyapi -n llms --reset` clears it (measured 2026-11-06).
- The proxy log shows two `GET /v0/management/usage-queue` a second: the manager's collector started in HTTP polling. With the proxy up, run `kubectl rollout restart deploy/cpa-manager -n llms` and check the transport under Verify.
- The proxy pod restarts in a loop: check the seed still sets `server.port`, and that the HelmRelease still sets `command`.
- A management write in the UI answers 500: `/data/config.yaml` is not writable.
- The manager cannot reach the proxy: check the proxy's NetworkPolicy admits the `cpa-manager` pods on 8317.
- Management requests from one client start failing: the app bans an address after five bad management keys, and `trusted-proxies` must stay the pod CIDR so the ban lands on the client, not the gateway.
- The manager's `data.key` is lost: the stored management key cannot be decrypted, and nothing else holds a copy of that file.
