This guide takes Firecrawl from the templates in Git to a working scraping API. Firecrawl scrapes, crawls and maps websites, searches the web and extracts structured data from pages. The deployment itself is in Git: the `[firecrawl]` section of `cluster.toml` and `kubernetes/apps/firecrawl/`. "Measured" below was run in Docker against `ghcr.io/firecrawl/firecrawl:2.11.816` on 2026-11-23, under the pods' restrictions (read-only root, every capability dropped, a non-root user), or on the cluster where it says live.

## What it is and is not

It is served at `https://firecrawl.${SECRET_DOMAIN}` on the internal gateway, and at `http://firecrawl-api.firecrawl.svc.cluster.local:3002` inside the cluster.

<Aside type="caution">
The self-hosted API has no login of its own. Firecrawl's authentication needs its cloud database schema, and the functions that look a key up are not published. The gateway asks for a key instead: a request to `https://firecrawl.${SECRET_DOMAIN}` needs `Authorization: Bearer <token>`, where the token is the `GATEWAY_API_KEY` field of the vault item `firecrawl`. A call to the Service inside the cluster passes no gateway and needs no key, so the NetworkPolicy decides who can make one. Each extract call spends the pooled CLIProxyAPI logins.
</Aside>

| Feature | Self-hosted |
| --- | --- |
| Scrape, crawl, map | Works. Measured. |
| Search | Works. It asks the AI KB SearXNG when `ai_kb.searxng` is on, and DuckDuckGo otherwise or when SearXNG returns nothing. |
| Extract and JSON-format scrapes | Need a model. They call CLIProxyAPI's Responses API, so page content leaves the cluster. |
| Screenshots and page actions | Do not work. They need Firecrawl's Fire-engine, which is not published. |
| Agent, Browser, interact, and the product, menu, audio and video formats | Cloud only. |

## What runs

One release holds four workloads, and the namespace has its own Redis.

- The API runs the HTTP server and every worker in one container, as Firecrawl's Compose file does.
- The Playwright service renders pages that need a browser.
- RabbitMQ and a queue Postgres carry the job queue. The Postgres is Firecrawl's own image, with `pg_cron` and its schema created at first start.
- The queue Postgres and RabbitMQ keep their data in the pod. A restart drops crawls in flight and stored results, which expire after 24 hours anyway. Nothing here is backed up.
- When the queue Postgres restarts, the API exits and its container restarts until the database is back. Measured live: about two minutes, with no step by hand.

## Fill the section

The section needs `[cliproxyapi]` and `[redis]`. Generate the queue database password, put it in the vault item `firecrawl` under the label `POSTGRES_PASSWORD` ([External Secrets and 1Password](/apps/external-secrets/)), and set `enabled = true` in the `[firecrawl]` section of `cluster.toml`:

```sh
openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 32; echo   # POSTGRES_PASSWORD
```

`model` names the model CLIProxyAPI runs for extract. It defaults to `claude-sonnet-5-5`, and any name the proxy lists at `/v1/models` works.

Then run `just template secrets-check`, `just configure`, commit and push.

The Kustomization and the HelmRelease are Ready, both ExternalSecrets are synced, and five pods are Running: the four workloads and `redis-0`. The `grep` prints nothing.

## Verify

Check that the API answers, then run one scrape:

```sh
curl -s https://firecrawl.${SECRET_DOMAIN}/v0/health/readiness
curl -s -m 75 -X POST https://firecrawl.${SECRET_DOMAIN}/v2/scrape \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com","formats":["markdown"],"timeout":60000}'
```

The first answers `{"status":"ok"}`. That is a heartbeat only. The second answers `"success":true` with Markdown, and proves the queue, the workers and outbound access together.

Extract goes through the model. Ask for a `json` format:

```sh
curl -s -m 75 -X POST https://firecrawl.${SECRET_DOMAIN}/v2/scrape \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com","formats":[{"type":"json","prompt":"Give the page title"}],"timeout":60000}'
```

A failure here while the plain scrape passes points at CLIProxyAPI: look in its log for a `/v1/responses` request.

## Clients

Point a client at the instance with its base URL and the gateway key:

- The Firecrawl CLI and the local MCP server read `FIRECRAWL_API_URL` and `FIRECRAWL_API_KEY`.
- The SDKs take an `api_url` or `base_url` option beside the key.
- A pod in the cluster uses the Service address. Its namespace has to be admitted by the `firecrawl-api` NetworkPolicy, which admits the `network` namespace, where the gateways run, and It's a Plan today.

It's a Plan uses the instance from release 1.14.0 of its fork on. Its HelmRelease allow-lists the Service host for plain http, and the credential is added in the app: Team settings, Integrations, Firecrawl, with the Instance URL `http://firecrawl-api.firecrawl.svc.cluster.local:3002` and no API key. That allow-list entry is trusted by every outbound path of the app, webhook targets and attachment import included.

## Updates

Firecrawl tags its API image several times a day, and publishes the Playwright and queue Postgres images as `latest` only. Renovate pins the two by digest and groups all three into one pull request on Monday, which is never merged without review. Read the release's `docker-compose.yaml` for new required variables before merging.

## Known limits

- One shared gateway key and no accounts, as above.
- With `[observability]`, Prometheus scrapes the queue metrics from a second listener on port 3003, which only the Prometheus pods can reach. There is no dashboard.
- Egress is limited to public addresses, the model proxy and the search engine. A scrape of a private address returns empty content with status 403. Measured live for private IP addresses and for hostnames that resolve to one.
- `/v2/extract` still answers but reports itself deprecated. Use `/v2/scrape` with a `json` format.
