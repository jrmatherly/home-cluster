The steps outside the repo that `[ai_kb]` in `cluster.toml` needs, in order. The deployment itself is in Git: the `[ai_kb]` section and `kubernetes/apps/ai-kb/`. The app's own repository is `<github account>/ai-kb`, which publishes the chart `oci://ghcr.io/<github account>/ai-kb/charts/ai-kb` and the four images (`ai-kb-app`, `ai-kb-ui`, `ai-kb-website`, `ai-kb-docreader`).

AI KB is served at `https://ai-kb.${SECRET_DOMAIN}` on both gateways. It has its own login, so the route carries no gateway `SecurityPolicy`. "Measured" below was run on the first deploy, 2026-10-17, against chart 0.3.0 and product v2026.10.17.1. Chart 0.4.1 with product v2026.10.18 went live on
2026-10-18 with files on RustFS, traces to Langfuse, Neo4j connected, registration in `invite_only`
mode and the egress fence. Chart 0.4.2 with product v2026.10.18.1 since 2026-10-19.

## What the app holds

Knowledge bases, their chunks and embeddings, users, tenants and the model and API-key settings each tenant enters live in the CloudNativePG cluster `ai-kb-db` (one instance, 10Gi, WAL archiving and a daily backup at 05:30 UTC through `components/postgres`). Uploaded files are on the `ai-kb-data-files` volume (`local-path`, 10Gi), which is why the `app` Deployment uses `Recreate`. The task queue and the chat streams are the namespace's Redis from `components/redis`.

The database loads `pg_search` from ParadeDB's extension image as an image volume (`docker.io/paradedb/paradedb-extension:0.26.2-18-trixie`; its Postgres major and Debian release must match the catalog image, which already ships pgvector). Three facts measured on the first deploy shape the Cluster manifest:

- The app's migrations run `ALTER EXTENSION pg_search UPDATE` (migrations 8 and 11), which only the extension's owner may, and a CNPG `Database` object creates extensions owned by `postgres`. So the Cluster's `postInitApplicationSQL` creates `uuid-ossp`, `vector`, `pg_trgm` and `pg_search` and hands them to the `app` role. It runs once, at initdb, before the app can connect, which also removes the race between the operator's `CREATE EXTENSION` and the app's first migration.
- The community pg_search refuses to start on a standby ("replicas are not supported on community and require paradedb enterprise"), so the cluster runs one instance, not the usual two.
- The first install predates both fixes. Its extensions were handed over by hand, `UPDATE pg_extension SET extowner = 'app'::regrole WHERE extname IN ('vector','pg_trgm','pg_search')` as `postgres` in the `app` database, and the broken second instance was removed with `kubectl cnpg destroy ai-kb-db 2 -n ai-kb`.

## cluster.toml

Section `[ai_kb]`, after `[ai_workspace.env]`:

- `jwt_secret`: at least 32 characters, from `openssl rand -hex 32`. Changing it signs everyone out.
- `aes_key`: exactly 32 letters and digits, from `openssl rand -hex 16`. It encrypts the API keys and credentials AI KB stores. Never change it: what it encrypted becomes unreadable.
- `admin_email`: the operator's address. The app promotes the account with this address to system administrator at startup, as long as no system administrator exists yet.

Then `just configure`, restore the sops files that did not change:

```sh
git checkout -- ':(glob)bootstrap/**/*.sops.*' ':(glob)kubernetes/**/*.sops.*' ':(glob)talos/**/*.sops.*'
```

Commit the rendered `kubernetes/apps/ai-kb/` and push. `just kube reconcile` makes Flux pull now.

### Files on RustFS

With `rustfs_access_key` and `rustfs_secret_key` set (generate them with `openssl rand -hex 16` and
`openssl rand -hex 32`; they need `[rustfs]`), the `ai-kb-files` bucket on RustFS becomes the
default storage backend: the chart's `STORAGE_TYPE` becomes `s3`, the `S3_*` settings point
at `http://rustfs-svc.rustfs.svc.cluster.local:9000` with path-style requests, the pair reaches the
app from `ai-kb-secret`, and `SSRF_WHITELIST_EXTRA` names the
RustFS Service, because the app's S3 client validates its endpoint through the same SSRF guard. The
namespace gets the `rustfs.storage/client` label that RustFS's NetworkPolicy admits, and the ai-kb
entry in `rustfs_consumers` makes the provisioning Job create the bucket and scope the pair to it.
A workspace created after the switch stores its files there. A workspace that exists keeps the
backend recorded at its creation (the data-files volume) until its default storage backend is
switched in the workspace settings, and files already uploaded are not moved (measured in the
app's source at the pinned tag: the startup migration only sets a default for a workspace that has
none). The ai-kb Kustomization depends on `rustfs-provision`, because the app checks its bucket at
startup.

### Traces in Langfuse

With `tracing = true` (it needs `[langfuse]`), AI KB sends traces to [Langfuse](/apps/langfuse/) in the AI KB project. AI
KB wraps its chat, embedding, rerank, VLM and ASR models and its knowledge ingest and post-process
paths in Langfuse tracers, so traces carry full prompts and answers and the chunk text of every
ingested document. It is off by default and on in this cluster since 2026-10-18, so Langfuse holds the same content
as AI KB, which is why it stays on the internal gateway behind the `cluster_admins` group. Langfuse creates the
project keys on its first start only, so a later change to the pair in `cluster.toml` must also be
made in Langfuse's project settings, or every export gets 401 silently. The app reads `LANGFUSE_HOST`, set to
`http://langfuse-web.langfuse.svc.cluster.local:3000`, `LANGFUSE_ENVIRONMENT` `home`, and the
project key pair from `[langfuse]`, which reaches it through `ai-kb-secret`; tracing turns on when
both keys are set. The exporter is the stock OTLP client, not the SSRF-safe one, so the host needs
no `SSRF_WHITELIST_EXTRA` entry (read in the app's source at the pinned tag). The namespace gets the
`langfuse.tracing/client` label that Langfuse's NetworkPolicy admits on port 3000.

### GraphRAG with Neo4j

With `neo4j_password` set (letters and digits, at least 32, from `openssl rand -hex 16`), the chart's own Neo4j runs in the namespace (image `neo4j:2026.09.0` from the chart, a Deployment with `Recreate` on a 10Gi `local-path` claim, `ai-kb-neo4j`), and the chart sets `NEO4J_ENABLE`, `NEO4J_URI` (`bolt://neo4j:7687`) and the `neo4j` user's credentials on the app. The password reaches the chart through the values document in `ai-kb-secret`. A knowledge base with graph extraction on makes extra LocalAI calls for every document it imports. Neo4j stores the password on its first start, so a later change must also be made inside Neo4j, or the app cannot sign in. The app tries Neo4j 30 times, two seconds apart, then exits (read in the app's source at the pinned tag), so on a fresh enable it restarts until Neo4j answers. The ingress NetworkPolicy admits the app pod on 7687.

### Web search with SearXNG

With `searxng_secret` set (letters and digits, at least 32, from `openssl rand -hex 32`), SearXNG runs in the namespace as its own Flux app, `searxng` (app-template, image `docker.io/searxng/searxng` pinned by digest), for the app's web search. It is internal only and answers JSON only: no HTTPRoute, `search.formats: [json]` (any other format gets 403), the image proxy and the rate limiter off, and a NetworkPolicy that admits only the app pod on 8080 and lets SearXNG reach DNS and public addresses on 80 and 443. Its `settings.yml` in the `searxng-settings` ConfigMap is a short override of SearXNG's defaults, mounted by `subPath` at `/etc/searxng/settings.yml`, because the entrypoint checks that the image's `/etc/searxng` directory exists and writes a settings file only when none is there. The secret is not in that file: it reaches the pod as `SEARXNG_SECRET`, which the app reads over `secret_key`, and without it the app refuses to start. The pod runs as uid 977 on a read-only root with every capability dropped, emptyDirs at `/tmp` (its SQLite caches) and `/var/cache/searxng` (the data directory the entrypoint checks), `enableServiceLinks: false`, and probes on `/healthz`. In Docker under that shape it used about 135 MiB idle and 150 MiB after eight concurrent searches, so it requests 192Mi. The Service host joins `SSRF_WHITELIST_EXTRA`, and the egress fence admits the SearXNG pod on 8080.

It queries SearXNG's default general engines (DuckDuckGo, Brave, Wikipedia, Wikidata, Google CSE and a few dictionary engines). From one home address some of them answer with a CAPTCHA or a rate limit at times, and SearXNG then suspends them and lists them under `unresponsive_engines`, so results thin out after a burst. Upstream suspends an engine for an hour after a CAPTCHA, three minutes after a rate limit or access denied, and 15 days after a Cloudflare CAPTCHA (read in SearXNG's `settings.yml`). Google, Bing and Startpage stay off, as they ship, because one address gets refused there fastest; the live check on 2026-10-18 got 20 results from Google CSE and Wikipedia while Brave and DuckDuckGo were suspended. The tags are `<year>.<month>.<day>-<commit>`, several per day, so a Renovate rule reads the date part as the version. Builds from the same day compare equal under that rule, so after a bump check that the pinned digest is the day's `latest`.

After the reconcile, add the provider in AI KB under Settings > Web Search: type SearXNG, Instance URL `http://searxng.ai-kb.svc.cluster.local:8080`, then use the test button. From the app pod, `curl -s 'http://searxng.ai-kb.svc.cluster.local:8080/search?q=test&format=json'` returns JSON with `results` and `unresponsive_engines`.

## Watch it come up

```sh
kubectl -n ai-kb get cluster,pods -w
kubectl -n ai-kb logs deployment/ai-kb-app | grep -i 'migration\|bootstrap'
```

Measured: the primary was ready 13 s after the Cluster appeared, the HelmRelease installed in under two minutes, and the app's log ends with `Database migrated from version 0 to 117` (117 on v2026.10.17.1). `AUTO_RECOVER_DIRTY` is on, so a failed migration leaves the pod running and `schema_migrations` dirty; the pod retries on its next start. To read the state:

```sh
kubectl -n ai-kb exec ai-kb-db-1 -c postgres -- psql -d app -c 'select version, dirty from schema_migrations'
```

## Sign-up and the first admin

Password sign-up stays open until the Pocket ID pair (`oidc_client_id` and `oidc_client_secret`) is set, because before that it is the only way to create an account. Anyone who can reach the form then gets a workspace (tenant) of their own, so the external gateway answers 404 for `POST /api/v1/auth/register` through the `ai-kb-not-found` HTTPRouteFilter on the `ai-kb-public` route, and accounts are created from the LAN, where `ai-kb.${SECRET_DOMAIN}` resolves to the internal gateway through UniFi DNS.

With the pair set, `DISABLE_REGISTRATION=true` puts the app in `invite_only` mode: the register form is hidden, and `POST /api/v1/auth/register` and registration by invitation are both refused. A new account then comes from a first Pocket ID sign-in, which creates it, or from a system administrator in the UI; an invitation only adds an account that exists to a workspace. The gateway's 404 stays as defence in depth. A registration mode saved in the UI (`auth.registration_mode` in the system settings, stored in the database) takes precedence over the env var (read in the app's source at the pinned tag).

The bootstrap only promotes an account that already exists, and it runs at startup, so the order is:

1. Create the `admin_email` account: from the LAN with the register form, or, once the Pocket ID pair is set, by signing in with Pocket ID as that address.
2. `kubectl -n ai-kb rollout restart deployment ai-kb-app`. The log then reads `[bootstrap] promoted user ... to system admin`.

Once a system administrator exists the env var grants nothing more, so a later revoke in the UI is not undone by a restart.

## Workspace settings from the environment

- `AIKB_IM_PLATFORMS` is `slack,telegram,mattermost`: a workspace can connect only those IM platforms, and the others get no adapter.
- `AIKB_AUDIT_RETENTION_DAYS` is `365`: audit log entries older than a year are deleted (the app's default is 90).
- `STORAGE_ALLOW_LIST` is `local,s3,minio`: the storage backends a workspace may pick.

## Pocket ID sign-in

A new client in Pocket ID, named `AI KB`:

- Callback URL: `https://ai-kb.${SECRET_DOMAIN}/api/v1/auth/oidc/callback` (exactly this; the login page builds it from the browser origin)
- Confidential client, scopes `openid profile email`; the app reads the email from `email` and the username from `name`, falling back to `preferred_username`

Copy the client ID and the secret into `oidc_client_id` and `oidc_client_secret` in `[ai_kb]`, then `just configure`, restore, commit, push and `just kube reconcile`. The HelmRelease adds the `OIDC_AUTH_*` env vars (the chart has no OIDC values), the secret comes from `ai-kb-secret`, and Reloader restarts the pod when that Secret changes. `SSRF_WHITELIST_EXTRA` names `auth.${SECRET_DOMAIN}`, because pods resolve it to the internal gateway's private address, which the app's SSRF-safe HTTP client refuses for discovery otherwise. A bad value is a crash loop, not a silent fallback: the app refuses to start when `OIDC_AUTH_ENABLE` is set without the client, secret and discovery URL.

Done when `GET /api/v1/auth/oidc/config` reports `enabled: true` with the display name `Pocket ID` and `GET /api/v1/auth/oidc/start` answers a 302 to Pocket ID. The first Pocket ID sign-in with an address that already has an account links to it; any other address gets a new account, which is why Pocket ID's "allow users to edit their own account details" stays off.

`OIDC_AUTH_EXTENSION_RETURN_URLS` names the browser extension's store-assigned return origins (Chrome Web Store, then Edge Add-ons), so its OIDC sign-in returns to the extension. Whether the Pocket ID client also needs those URLs as callbacks is not recorded.

## Models and keys
LocalAI's models arrive declaratively. The `ai-kb-models` ConfigMap is the app's `builtin_models.yaml` (`BUILTIN_MODELS_CONFIG` names the mount), which the app upserts into its `models` table on every start as built-in defaults visible to every workspace: the chat model `qwen-3.5-4b` (`KnowledgeQA`, context window 16384, one LocalAI slot) and the embedding model `nomic-embed-text-v1.5` (768 dimensions), both provider `generic` at `http://localai.ai.svc.cluster.local:8080/v1` with the key as `${LOCALAI_API_KEY}` from `ai-kb-secret`. Removing an entry from the ConfigMap retires that model on the next start; a model added in the UI is never touched by the loader. Other providers and their API keys are entered per tenant in the app's settings and stored encrypted with `aes_key` in the database.
The ai-kb namespace carries the `localai.ai/client` label that LocalAI's NetworkPolicy admits, and `SSRF_WHITELIST_EXTRA` on the app names `localai.ai.svc.cluster.local`, because the Service resolves to a cluster address the app's SSRF-safe HTTP client refuses otherwise (measured 2026-10-18: the pod's own curl listed both models once the label and allowlist were in place).

## Network

A NetworkPolicy admits the `network` namespace on 8080 (the three web containers) and the chart's own pods on 8080 (frontend to app for `/files` and the embed-frame policy), and only the app pod on 50051 (docreader) and, when Neo4j is on, 7687. The HTTPRoute mirrors the chart's Ingress: `/api` to `app`, `/docs` to `website`, everything else to `frontend`. The app trusts the forwarded client address, so the gateway must stay the only path. A second NetworkPolicy, `ai-kb-egress`, fences the app pod's egress: DNS in `kube-system`, its Postgres (`cnpg.io/cluster: ai-kb-db`) on 5432, Redis on 6379, docreader on 50051, and, when each is on, Neo4j on 7687, LocalAI in `ai` on 8080, the `network` namespace and the internal gateway's own address on 443 for Pocket ID (pods resolve its host to the gateway; the address rule covers the case where the policy sees the packet before Cilium translates it to an Envoy pod), RustFS on 9000, Langfuse on 3000 and SearXNG on 8080; everything else is TCP 80 and 443 to public addresses only, never the RFC 1918 ranges, link-local, CGNAT or the pod, service and node CIDRs. Endpoints a workspace configures (web search, IM, MCP servers, connectors) must be on the internet, and the app's SSRF allowlist is the app-side gate for them.

## Verify

After a rollout that changes the NetworkPolicies, check that the app still reaches Pocket ID through the egress fence, and that nothing the app needs is dropped:

```sh
kubectl -n ai-kb exec deploy/ai-kb-app -- wget -qO- https://auth.${SECRET_DOMAIN}/.well-known/openid-configuration
hubble observe -n ai-kb --verdict DROPPED
```

The first prints Pocket ID's discovery document. The second should show no drops from the `ai-kb-app` pod to a dependency it needs.

Measured from the app pod on 2026-10-18, once the fence was live: Pocket ID, LocalAI, RustFS and an
internet host answered, and a LAN address was blocked.

## Updates

The chart is pinned by `OCIRepository` tag and the four images by `tag@sha256:digest`; Renovate follows both. The pg_search extension image is a CNPG `image.reference`, which no built-in Renovate manager reads, so `.renovaterc.json5` carries a `customManagers` regex rule for it; Docker versioning keeps it on `-18-trixie` tags. When the catalog image moves to a new Postgres major or Debian release, move the extension image with it in the same change.
