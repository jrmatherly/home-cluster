The steps outside the repo that `[langfuse]` in `cluster.toml` needs, in order. The deployment
itself is in Git: the `[langfuse]` section and `kubernetes/apps/langfuse/`. "Measured" below was
run in Docker against `langfuse/langfuse:4.63.0`, `langfuse/langfuse-worker:4.63.0` and
`clickhouse/clickhouse-server:26.4.5.143` on 2026-10-18, under the pods' restrictions (read-only
root, every capability dropped, the pods' uids). It went live on 2026-10-18, with the web and worker
pods Ready at `langfuse.${SECRET_DOMAIN}`.

## What it holds

Langfuse is an LLM tracing UI. AI KB sends it one trace per chat, with the full prompt and answer,
so treat its data like AI KB's own. It needs four stores, all in the `langfuse` namespace or on the
cluster:

- Postgres: the CloudNativePG cluster `langfuse-db` (two instances, WAL archiving, a daily backup
  at 05:45 UTC) holds users, projects and API keys.
- ClickHouse: one StatefulSet `clickhouse` with a 20Gi `local-path` volume holds the traces. It has
  one replica and no backup, so a lost node loses the trace history but nothing else. Trace
  retention is an Enterprise feature, so the volume is the ceiling; measure it after a month with
  `kubectl -n langfuse exec clickhouse-0 -- du -sh /var/lib/clickhouse`.
- Redis: the namespace's own, from `components/redis`, holds the ingestion queues.
- S3: the `langfuse-events` bucket in RustFS holds every raw event before the worker processes it.
  Langfuse reads those objects back for trace detail, so the bucket has no expiry and grows with
  tracing. Measure it after a month.

The UI is at `https://langfuse.${SECRET_DOMAIN}` on the internal gateway only.

## Pocket ID client

In the Pocket ID admin UI, create an OIDC client:

- Name: Langfuse.
- Callback URL: `https://langfuse.${SECRET_DOMAIN}/api/auth/callback/custom`.
- Allowed user groups: `cluster_admins`.

Every user the client admits joins the Home organization as an admin on first sign-in, so the
group restriction is the access control. Admin is the default role (`LANGFUSE_DEFAULT_ORG_ROLE`)
rather than owner, because an owner can delete the organization; a membership that exists keeps its
role. The sign-up onboarding step is off (`LANGFUSE_DISABLE_SIGNUP_ONBOARDING`), because it calls
langfuse.com from the browser. The password form is off.

## Keys

Generate each value once:

```sh
echo "pk-lf-$(uuidgen | tr A-Z a-z)"                              # public_key
echo "sk-lf-$(uuidgen | tr A-Z a-z)"                              # secret_key
openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 48; echo     # salt, then again for nextauth_secret
openssl rand -hex 32                                              # encryption_key
openssl rand -base64 48 | tr -dc A-Za-z0-9 | head -c 32; echo     # clickhouse_password
openssl rand -hex 16                                              # rustfs_access_key
openssl rand -hex 32                                              # rustfs_secret_key
```

Never change `salt` (every API key stops working) or `encryption_key` (stored LLM and integration
keys become unreadable). Changing `nextauth_secret` signs everyone out.

## cluster.toml

Section `[langfuse]`, after `[rustfs]`: the eight generated values above, plus `oidc_client_id`
and `oidc_client_secret` from the Pocket ID client. It needs `[postgres.backup]`, `[redis]`,
`[pocket_id]` and `[rustfs]`.

Then `just configure`, restore the sops files that did not change:

```sh
git checkout -- ':(glob)bootstrap/**/*.sops.*' ':(glob)kubernetes/**/*.sops.*' ':(glob)talos/**/*.sops.*'
```

Commit the rendered `kubernetes/apps/langfuse/` and the changed `kubernetes/apps/rustfs/`, then
push. `just kube reconcile` makes Flux pull now.

## First start

```sh
kubectl -n rustfs logs job/rustfs-provision
kubectl -n langfuse get pods,pvc
kubectl -n langfuse logs deploy/langfuse-web
```

The provisioning log ends with `provisioned langfuse in langfuse-events`. The web log lists every
Prisma migration, then the ClickHouse migrations, then `Running init scripts...`. Measured in
Docker: 457 Postgres migrations and the ClickHouse migrations took 18 seconds on a laptop, after
which `/api/public/ready` answered OK. On the cluster the startup probe allows ten minutes, because
the chart's own probes kill the pod part way through a first start (langfuse-k8s issues 272 and
427), which leaves a failed migration behind.

On that first start Langfuse also creates the Home organization, the AI KB project and the
project's key pair from `public_key` and `secret_key`. It creates them only when they are absent, so
a later change to the pair in `cluster.toml` must also be made in the project's settings.

The web and worker pods run with `enableServiceLinks: false`, set by a `postRenderers` patch
because the chart has no switch for it. Without it the kubelet injects a Docker-link variable set
for every Service in the namespace, among them `REDIS_PORT=tcp://<address>:6379` from the `redis`
Service. Langfuse's env schema reads `REDIS_PORT` as a number, gets NaN and refuses to start. That
is how both pods failed on the first rollout.

## Sign in

Open `https://langfuse.${SECRET_DOMAIN}` from the LAN and pick Pocket ID. The first sign-in creates
the account and makes it an admin of Home. Open the AI KB project and check Settings, API keys: the
public key matches `public_key`.

## LLM connection

With NVIDIA on, the `langfuse` namespace carries the `localai.ai/client` label, so LocalAI's
NetworkPolicy admits it. Both the web and worker pods put `localai.ai.svc.cluster.local` on
Langfuse's LLM connection host allowlist, because self-hosted Langfuse refuses a connection whose
base URL resolves to a private address, and the worker runs the evaluators.

In the AI KB project, open Project Settings, LLM Connections, and add a project connection:

- Adapter: OpenAI.
- API key: the LocalAI API key, `api_key` in `[localai]`.
- Base URL, under Advanced Settings: `http://localai.ai.svc.cluster.local:8080/v1`.
- Custom model names: `qwen-3.5-4b`, because the Playground otherwise offers only the adapter's
  default models.

Organization-level connections are an Enterprise feature, so the connection belongs to the project.
To prove the path, open any `chat.completion` generation in the traces and open it in the
Playground. A reply from `qwen-3.5-4b` means the connection works.

## Verify

```sh
kubectl -n langfuse get pods
kubectl -n langfuse get deploy langfuse-web langfuse-worker -o jsonpath='{range .items[*]}{.metadata.name} {.spec.template.spec.enableServiceLinks}{"\n"}{end}'
```

Every pod Running and Ready, and both Deployments print `false`.

Measured on the first rollout, 2026-10-18: the chart's first install waits until its pods are
ready, so a fix pushed to the HelmRelease while that install hangs is not applied until the
HelmRelease's 15-minute timeout runs out. To skip the wait, patch the Deployments by hand with the
same change. The pods then come up and the install finishes, and the HelmRelease already carries
the change, so nothing drifts:

```sh
kubectl -n langfuse patch deployment langfuse-web --type merge -p '{"spec":{"template":{"spec":{"enableServiceLinks":false}}}}'
kubectl -n langfuse patch deployment langfuse-worker --type merge -p '{"spec":{"template":{"spec":{"enableServiceLinks":false}}}}'
```

## Updates

Renovate offers the chart, the two Langfuse images (keep them on the same version) and the
ClickHouse image. The web pod runs the migrations, and on v4 they are not all additive, so a
rollback needs more than an image swap. ClickHouse must stay on a version Langfuse supports
(25.12 or later, 26.4 recommended). The `postRenderers` patches find the `langfuse-web` and
`langfuse-worker` Deployments by name, so check those names on a chart bump.

## If something breaks

- The web pod restarts during its first start: check the log for `P3009`, which names a failed
  migration. Prisma's documented recovery is `prisma migrate resolve --rolled-back <migration>`,
  run from the web image against the same database, then a restart.
- Traces never appear: check `kubectl -n langfuse logs deploy/langfuse-worker` for S3 errors, and
  that the provisioning Job ran after the key pair was added.
- ClickHouse is near its 4Gi limit: the system log tables Langfuse never reads are already off, so
  look at `system.parts` for the largest table.
