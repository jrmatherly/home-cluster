# Firecrawl (`[firecrawl]`)

- `[firecrawl]` in `cluster.toml` (`enabled`, needing `[cliproxyapi]` and `[redis]`; `model`, default `claude-sonnet-5-5`, is the `MODEL_NAME` of every model call; the vault item `firecrawl` holds `POSTGRES_PASSWORD`, at least 24 letters and digits, and `GATEWAY_API_KEY`, at least 32) gates the `firecrawl` namespace, which enforces the `restricted` pod security level. `firecrawl/firecrawl` is a self-hosted Firecrawl (`firecrawl/firecrawl`), a web scraping API with scrape, crawl, map, search and extract, at `firecrawl.${SECRET_DOMAIN}` on the internal gateway and at `firecrawl-api.firecrawl.svc.cluster.local:3002` in the cluster. It exists so It's a Plan's agents and later apps do not need the paid cloud API. The plan is `docs/superpowers/plans/2026-11-23-firecrawl.md` (gitignored). Live since 2026-11-23 at `f6d33c19`; the last bullet holds what the first rollout measured, and "Docker" marks what was measured only there.
- No login. Firecrawl's authentication is all or nothing (`apps/api/src/lib/withAuth.ts`, `controllers/auth.ts` and `db/rpc.ts` at `v2.11.816`, read): with `USE_DB_AUTHENTICATION` unset or false every request gets a fixed "bypass" team, key or no key; with it true every key is looked up through SQL functions over `DATABASE_URL` in Firecrawl's cloud schema of teams, keys and plans. That lookup is plain Postgres through drizzle at this version, not the Supabase client, but the schema has to be provisioned first and `SELF_HOST.md` does not document it. Read on 2026-11-23 at `v2.11.816`: the tables are published as a drizzle schema (`apps/api/src/db/schema/public.ts`, 42 tables including `teams`, `api_keys`, `users`, `subscriptions`, `prices`; a maintainer pointed self-hosters at it in issue 1797 on 2026-06-11), with no migration files and no drizzle config in the tree. The SQL functions the lookup calls (`auth_chunk_2`, `auth_chunk_2_from_team` and 13 more in `db/rpc.ts`) are defined nowhere on GitHub: a code search finds only their callers. `teams.hmac_secret` defaults to `extensions.gen_random_bytes`, a Supabase schema. So turning it on means pushing the tables with drizzle-kit, writing `auth_chunk_2` by hand from the columns `controllers/auth.ts` reads, seeding an org, a team and a key, and re-checking all of it against an image tagged several times a day. Not built, and not worth it for one LAN key. There is no static-key mode: `TEST_API_KEY` is a test setting. So a key can only be enforced in front of Firecrawl. The installed Envoy Gateway (1.10.0) has `apiKeyAuth` in its SecurityPolicy, which would cover the LAN route and not a call to the Service; by the docs it accepts `Authorization: Bearer <key>` with the bare key in the Secret (Envoy Gateway's v1.10 API Key Authentication page; Envoy's `api_key_auth` `KeySource.header` strips a leading `Bearer` and its space), and the live measurement below agrees. Jason first chose on 2026-11-23 to serve it on the LAN with no key, then asked the same day for the gateway key: `securitypolicy.yaml.j2` puts `apiKeyAuth` on the `firecrawl` HTTPRoute, reading the `Authorization` header against the Secret `firecrawl-gateway-keys`, which `gateway-externalsecret.yaml.j2` builds with one client ID, `lan`, from the vault field `GATEWAY_API_KEY`. The policy has no flag: it renders whenever `firecrawl_enabled`, so the field must exist before the push, or the route fails closed. Measured live at `325dc8a4` on Envoy Gateway 1.10.0: `/v0/health/readiness` answers 401 with no key and with a wrong key, 200 with `Authorization: Bearer <key>` and also 200 with the bare key in that header, and a `/v2/scrape` with the key succeeds. Since `abb48dc0` the policy sets `sanitize: true`, so the gateway removes the key before forwarding and Firecrawl never sees it; the same three answers and the scrape were measured again after it. Every pod in `network` can still call the API on 3002 with no key, because the policy admits the whole namespace, as every app's does here; narrowing it to the Envoy pods is not done. The boundary for in-cluster callers is still the `firecrawl-api` NetworkPolicy, which admits the `network` namespace and, when `itsaplan_enabled`, the `itsaplan` namespace on 3002, and with `observability_enabled` the Prometheus pods (`app.kubernetes.io/name: prometheus` in `observability`, the label read live) on 3003, not the whole namespace, because that listener has no key.
- Metrics, with `observability_enabled`: `ADMIN_INTERNAL_PORT: 3003` and `ADMIN_INTERNAL_HOST: 0.0.0.0` start the API's keyless admin listener, the `firecrawl-api` Service gains the port `metrics`, and the chart's `serviceMonitor` scrapes `/admin/metrics` and `/admin/nuq-metrics` every 60 s (both `text/plain`, read in `controllers/admin/metrics.ts`; the ServiceMonitor and Service checked with `helm template` on 5.3.0). That listener also serves the queue UI at `/admin/queues`, `GET /admin/precrawl`, which queues a run, `POST /admin/fsearch`, `POST /admin/crawl-monitor`, `/admin/redis-health`, `/admin/feng-check`, `/admin/index-queue-prometheus` and `/admin/nuq-fdb-metrics` (`routes/admin.ts`, read by a reviewer), so only the policy keeps them to Prometheus. Each endpoint carries a `metrics_path` label from `__metrics_path__`, because two paths on one port otherwise write one `up` series (measured before the label: ten samples in five minutes in one series; after it, one `up` series per path). A scrape of `/admin/metrics` is not read-only: it removes empty queue keys from the Redis set `concurrency-limit-queues`, upstream's own cleanup (`controllers/admin/metrics.ts`, read by a reviewer). 3003 is free among the harness's ports (3000, 3002, 3004 to 3012 in `config.ts`). Measured live at `325dc8a4`: Prometheus reports both targets `up`, with series such as `nuq_pool_total_count` and `concurrency_limit_queue_job_count_total` under `job="firecrawl"`, and a request to port 3003 from the It's a Plan api pod times out.
- The API's init container `wait-for-postgres` runs the API image and loops on a TCP connect to `firecrawl-postgres:5432`, which opens only after `nuq.sql` has run. Without it, any rollout that recreates the API and Postgres together left the API with two restarts: at `325dc8a4` both pods were created in the same second, the prefetch worker got `EHOSTUNREACH`, and the harness exited with code 1 until Postgres was Ready six seconds later (measured). The script exits 0 against the live database and keeps retrying against a closed port (run in the live pod). Seen live at `82c2555f`: the init container exited 0 and the pod came up with no restart. It does not help when Postgres restarts under a running API: that still costs API container restarts, as at `abb48dc0`, which changed only the Postgres pod and left the API with two, cleared by deleting the API pod. The race itself, both pods recreated together with the init container in place, has not been exercised.
- The queue Postgres starts with `-c min_wal_size=256MB -c max_wal_size=2GB` (`args`, which the entrypoint passes to `postgres`, and which override `postgresql.auto.conf`). The image's `nuq.sql` sets `min_wal_size` to 4GB and `max_wal_size` to 16GB with `ALTER SYSTEM`, and below the floor Postgres recycles WAL segments and never removes them, so `pg_wal` alone would have grown to 4GB inside the 5Gi `sizeLimit` and the kubelet would have evicted the pod under load. Measured live at `abb48dc0`: `SHOW` returns 256MB and 2GB, `pg_cron` is still preloaded and the four `nuq` tables exist. Not measured under load: the 1Gi `/tmp` on the API pod, where upstream downloads PDFs and documents, and RabbitMQ's 1Gi, whose free-disk alarm reads the node filesystem and not the limit (a reviewer's inference). An emptyDir reports no `kubelet_volume_stats` series, so nothing warns before an eviction.
- One app-template release, four controllers, each a Deployment with `Recreate`, a read-only root and every capability dropped: `api` (`ghcr.io/firecrawl/firecrawl`, uid 1000, `node dist/src/harness.js --start-docker`, which runs the API and every worker in one container as upstream's Compose file does), `playwright` (`ghcr.io/firecrawl/playwright-service`, uid 1000), `rabbitmq` (`docker.io/library/rabbitmq:3-management`, uid 999) and `postgres` (`ghcr.io/firecrawl/nuq-postgres`, uid 999). The chart names the Services `firecrawl-<controller>` and labels pods `app.kubernetes.io/controller` (measured with `helm template` on 5.3.0). Redis is the namespace's own instance from `components/redis` at `redis:6379`, with the password from `redis-auth` in both `REDIS_URL` and `REDIS_RATE_LIMIT_URL`; the chart sorts env names, so `REDIS_PASSWORD` precedes the two URLs that expand it (checked in the render). `enableServiceLinks` is false, because the Services would inject `FIRECRAWL_*_PORT` variables. The upstream Helm chart is not used: it splits the workers into Deployments that request over 25 G and defaults to third-party images.
- The Playwright command is `node dist/api.js`, not the image's `pnpm start`: corepack downloads pnpm into a home directory that does not exist and exits on the read-only root (Docker, 2026-11-23).
- The queue Postgres is Firecrawl's own image: Postgres 17 with `pg_cron` preloaded on the `postgres` database, and `nuq.sql` creating `pgcrypto`, `pg_cron` and the `nuq` schema at initdb only. So `POSTGRES_DB` stays `postgres`, and the database is not a CloudNativePG cluster. It, RabbitMQ and every `/tmp` are `emptyDir`: a pod restart loses in-flight crawls and stored results, which expire after 24 hours anyway, and a new Postgres pod runs `nuq.sql` again. `PGDATA` is a subdirectory, because initdb refuses a mount root it does not own. Reloader restarts `api` and `postgres` together when any key of `firecrawl-secret` changes, the proxy's client key included, so a rotation of either empties the queue, and the fresh `emptyDir` takes a new password. The Postgres probes run `pg_isready` over TCP with a startup probe of five minutes: the entrypoint's init server listens on the socket only, and a liveness restart during a slow initdb would leave a partial `PGDATA` that only a pod delete clears. The only claim in the namespace is Redis's 1Gi. Nothing here is backed up.
- Model calls go to `OPENAI_BASE_URL=http://cliproxyapi.llms.svc.cluster.local:8317/v1` with CLIProxyAPI's client key (the `cliproxyapi` item's `API_KEY`, read into `firecrawl-secret` as `OPENAI_API_KEY`). Firecrawl calls the Responses API, `POST /v1/responses`, for extract and for a `/v2/scrape` with a `json` format (Docker, with a stub in place of the model), and CLIProxyAPI answered that path for `claude-haiku-5-5` with a completed response (Jason, on the cluster, 2026-11-23). The full path from Firecrawl to the proxy has not run. Page content leaves the cluster, and extract draws on the same Claude logins as Claude Code. With the model endpoint answering 500, scrape, map, crawl and search still passed (Docker). `/v2/extract` reports itself deprecated in favour of the `json` format, and answers with `Sunset: Thu, 10 Dec 2026 15:00:00 GMT` (measured live, 2026-11-23); by Firecrawl's source this build answers 410 after that time, by its own clock, which is not tested. So a caller still on `/v2/extract`, It's a Plan up to 1.13.1 included, stops working then. With no model configured, a `json`-format scrape answers 500 with a generic `UNKNOWN_ERROR` body, and only the server log names the missing key (Docker). `/v2/team/queue-status` answers a JSON 200 with no key, which the It's a Plan fork plans to use as its credential check.
- Search tries Fire-engine (not published), then SearXNG when `SEARXNG_ENDPOINT` is set, then DuckDuckGo (`apps/api/src/search/v2/index.ts` at `v2.11.816`, read). The endpoint is rendered only when `ai_kb_searxng`, as `http://searxng.ai-kb.svc.cluster.local:8080`, and that SearXNG's policy then admits the API pod. Search answered with no endpoint set (Docker). From one home address some SearXNG engines are suspended at times, so the fallback may answer instead.
- What a self-hosted stack cannot do: screenshots and page actions need Fire-engine (a screenshot request fails with `Engines tried: []`, Docker), and Agent, Browser, interact and the product, menu, audio and video formats are cloud-only or need undocumented services. `/v2/team/credit-usage` answers 500 with a JSON body, which is why It's a Plan's credential check needs the fork change below.
- Egress. The API fetches pages itself as well as through Playwright, so `firecrawl-api` allows DNS, the namespace's pods on their four client ports (3000, 5432, 5672, 6379, which leaves RabbitMQ's management port closed), CLIProxyAPI on 8317, SearXNG on 8080 when deployed, and public addresses over TCP with `private_cidrs` excluded (no UDP, so no HTTP/3); `firecrawl-playwright` allows DNS and those public addresses; `firecrawl-backends` gives RabbitMQ and Postgres no egress. Firecrawl has a guard of its own: a scrape of a private container address returned success with empty Markdown and the target saw no request (Docker). Whether it holds for a hostname that resolves to a private address is not measured. The network fence cannot stop a scrape that names a destination the API needs anyway: Redis, Playwright, RabbitMQ and Postgres on those ports, the proxy on 8317 and SearXNG on 8080 are left to Firecrawl's guard, with Redis's password and the proxy's key as the second wall (found in review, 2026-11-23).
- Measured in Docker on 2026-11-23, on API `2.11.816`: ready in about 12 seconds; after the tests the API held 2.2 GiB, Playwright 190 MiB, Postgres 134 MiB, RabbitMQ 128 MiB and Redis 11 MiB. The requests and limits come from those numbers and upstream's Compose limits (8 G and 4 G). RabbitMQ accepts its default `guest` account from another pod: the image's `/etc/rabbitmq/conf.d/10-defaults.conf` sets `loopback_users.guest = false` (read from the pinned `3-management` image, 2026-11-23), and `firecrawl-backends` admits only the API pod. If an `ACCESS_REFUSED` line ever shows in the API log, the fix is `RABBITMQ_DEFAULT_USER` and `RABBITMQ_DEFAULT_PASS` from a vault field, carried in `NUQ_RABBITMQ_URL`.
- Updates. The API image is tagged several times a day, and the Playwright and Postgres images publish `latest` only. `.renovaterc.json5` pins the two by digest, keeps all three out of the Tier 1 digest automerge and groups them into one Monday PR that is never automerged, with a three day minimum release age. RabbitMQ is held on 3.x by its own rule, because upstream's Compose file pins `rabbitmq:3-management` and the 3.x images are no longer built from the official repository's main branch; its digest PRs are rebuilds of that tag and merge under Tier 1. Move it to 4 only when Firecrawl's Compose file does. A new Postgres digest takes effect on the next pod, whose `emptyDir` is new. Read the release's `docker-compose.yaml` diff before merging.
- It's a Plan reaches this instance from fork release 1.14.0 on (published 2026-11-23; pinned in its templates the same day, see the last sentences of this bullet for what is still unproven). Up to `v1.13.1` its Firecrawl client was fixed to the cloud address. Two commits on the fork's `main` change that. `cad2d009` gives the credential an optional Instance URL, written without `/v2`; the API key stays required, so any text goes there, and the credential check reports that it cannot be checked automatically and still saves, because `/v2/team/credit-usage` answers 500 here. `dd63610a` lets an `SSRF_ALLOWED_HOSTS` entry written as `http://host` permit plain http to that exact host (`packages/net/src/index.ts`, read at `dd63610a`; a bare hostname stays https only, and Jason chose this). So It's a Plan's HelmRelease sets `api.env.SSRF_ALLOWED_HOSTS` to `http://firecrawl-api.firecrawl.svc.cluster.local` when `firecrawl_enabled`, with no port, path or trailing slash, because an entry with `:3002` matches nothing; chart 1.14.0 renders it into the `itsaplan` ConfigMap, which the api, web and worker Deployments all read (measured with `helm template`, 2026-11-23). In 1.14.0 the API key is optional, the credential check calls `/v2/team/queue-status` and reports valid on a JSON 200, and the extract tool sends one `/v2/scrape` with a `json` format per page instead of `/v2/extract` (reported by the It's a Plan session). The Instance URL is `http://firecrawl-api.firecrawl.svc.cluster.local:3002`, and the `firecrawl-api` policy admits the `itsaplan` namespace for it. A host named there is trusted in cleartext by every outbound path of the app that reads the list: project webhooks, attachment import by URL, git connections and agent endpoints. A member who can import an attachment by URL can therefore send a GET to Firecrawl's API and read the answer, and no NetworkPolicy here changes that. A `.local` name is not looked up or pinned by the guard; cluster DNS resolves it at connect time. A tool call from the app through its guard to that address has not run; a `wget` from the api pod did answer. The route through the gateway, `https://firecrawl.${SECRET_DOMAIN}` with the bare hostname allow-listed, also works and needs only `cad2d009`, plus, since the gateway key, that key in the credential's API key field.

Scrape, map and crawl pass. Search logged `Using searxng search` with no DuckDuckGo line after it. - Upstream docs review, 2026-11-23: `SELF_HOST.md`, `docker-compose.yaml` and both Kubernetes example READMEs are byte-identical at `main` and `v2.11.816`, and the public guide (`docs.firecrawl.dev/contributing/self-host`, pinned to `v2.11.162`) adds nothing on a schema. This release matches them on the image source (official `ghcr.io` images by digest), `POSTGRES_DB`, no admin routes on the API port, private dependency ports and a NetworkPolicy. Differences found: the public guide says screenshots and page actions need Fire-engine, so they are not available here (not tested); it asks for a database password of at least 32 characters against the 24 the validator asks for; the API idled at about 2150Mi against a 2Gi request (measured twice), so the request is now 2560Mi; the `emptyDir` volumes carried no `sizeLimit`, where Compose caps Playwright's cache at 1G, so each `/tmp` and RabbitMQ's data are now 1Gi, the queue database 5Gi and its socket directory 16Mi (they held 0, 15M, 42M and 4K when measured idle), and a pod that passes its limit is evicted, which empties the queue; and the metrics listener, above. Checked and fine: the pod's open-file limit is 1048576 against Compose's 65535, `/health/readiness` and `/v0/health/readiness` both answer 200, and the worker and harness ports Compose sets equal the defaults in `config.ts`. A deleted API pod comes back Ready with a 200 readiness in under three minutes (measured when clearing the restart counter).
