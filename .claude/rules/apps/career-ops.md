# career-ops (`[career_ops]`)

- `[career_ops]` in `cluster.toml` (two Pocket ID clients made by hand, one Claude credential (the OAuth token, or `anthropic_base_url` with `anthropic_auth_token`), two secrets of at least 32 characters and a list of allowed emails, set all together, needing `[pocket_id]`, `[volume_backup]` and `ingress.mode` `cloudflare-tunnel`) gates the `career-ops` namespace, which enforces the `restricted` pod security level. `career_ops_enabled` keys on `oidc_client_secret`. The `public` fixture sets the section.
- `career-ops/career-ops` is the job-search dashboard, `ghcr.io/jrmatherly/career-ops-server`, at `career.${SECRET_DOMAIN}` on the internal gateway, plus the external one with `public = true` (which needs `pocket_id.public`). A SecurityPolicy on its HTTPRoute signs users in with Pocket ID and admits only `cluster_admins`; the app has no login of its own. The route's request timeout is 900 s because the `/api/run` event stream lasts up to 800 s. The Service is renamed `career-ops-web` with `forceRename`.
- One replica with `strategy: Recreate`, because `lib/dir-lock.mjs` judges lock staleness by pid and a second pod would take the first one's locks for stale. `/data` (tracker, reports, CVs) and `/home/app` (the Claude CLI's `~/.claude`) are retained `local-path` claims `career-ops-data` and `career-ops-home`; `/tmp`, `/home/app/.cache`, Next's image cache at `/app/web/.next/cache` and a 1Gi memory `/dev/shm` for Chromium are emptyDirs on the read-only root. The publish container gets `HOME=/tmp` for the same reason.
- The app's request guard admits loopback hosts and the hosts in `CAREER_OPS_WEB_ALLOWED_HOSTS` (`career.${SECRET_DOMAIN}`, which also makes it bind `0.0.0.0`), and refuses the pod IP the kubelet sends, so the probes and the scan tick send `Host: localhost`. Any client can send that header, so the gateway is the access control: the NetworkPolicy admits only the `network` namespace and pods labelled `career-ops.io/role: scan-tick` on port 3000.
- The web pod's readiness probe is `test -f /data/data/applications.md`, the backup job's sentinel, because `/api/healthz` never reads `/data` and a recreated claim binds to a new empty `local-path` volume (the PV's reclaim policy is `Delete`, read live 2026-11-10) that looks like a fresh install. On an empty volume the pod runs unready: the gateway answers 503 and the scan tick fails. Restore a backup with `kubectl exec` into that pod, or for a deliberate fresh install create the file (`kubectl exec -n career-ops deploy/career-ops -- sh -c 'mkdir -p /data/data && touch /data/data/applications.md'`; that the app reads an empty file as an empty tracker is unverified). Startup and liveness still probe `/api/healthz`.
- Scans run inside the web pod (`CAREER_OPS_SCHEDULER=external`). The CronJob `career-ops-scan-tick` POSTs `/api/scheduler` every 15 minutes with a digest-pinned `curlimages/curl`.
- `career-ops/publish` is the share-page service, `ghcr.io/jrmatherly/career-ops-publish`, at `cv.${SECRET_DOMAIN}` on the external gateway only, with no SecurityPolicy: share pages are public and the account page has its own Better Auth sign-in through the second Pocket ID client. Pocket ID must report `email_verified: true` for the addresses in `publish_allowed_emails`, or the sign-in is refused. Its SQLite database is the retained claim `publish-data`. Its probes are `tcpSocket`, because the service has no health route and listens only after `auth migrate` succeeded. Its NetworkPolicy admits only the `network` namespace.
- `PUBLISH_TRUSTED_PROXIES` is the pod CIDR, but `server.mjs` matches peers by exact address today, so the CIDR never matches and every visitor keys as the Envoy pod address until career-ops matches CIDRs: one shared password-attempt budget and one viewer an hour. The client header stays the image default `cf-connecting-ip`, which Cloudflare overwrites, never `x-forwarded-for`, whose leftmost entry is whatever the visitor sent; that is why the section needs `ingress.mode` `cloudflare-tunnel`. `PUBLISH_ALLOWED_EMAILS` lives in `publish-secret`, so no address at the domain is committed in clear.
- The dashboard's share features (`/api/shares*`) read `PUBLISH_URL` and `PUBLISH_API_KEY` from the pod env first, then from `/data/.env`: the optional `publish_api_key` (minted after the first deploy at `cv.${SECRET_DOMAIN}/account`, which has no link from the share pages; sign-in there needs the publish client's UUID client ID, not its secret, measured 2026-11-08) renders `PUBLISH_API_KEY` into `career-ops-secret` and `PUBLISH_URL` into the HelmRelease, and reloader restarts the pod. No `/data/.env` is needed then. Both backup jobs fail nightly until the volumes hold data (`/data/data/applications.md`, and a first signed-in user in `publish.db`), and `KubeJobFailed` stays firing until the failed Job is deleted; that is the house pattern, so expect it between the first deploy and the migration.
- Two volume-backup CronJobs upload to the `[volume_backup]` bucket and prune after 7 days, each in its own folder so one job's prune never removes the tars a failing other job left: `volume-backup` (01:50 UTC) tars `/data` read-only in the server image's GNU tar to `volumes/career-ops/career-ops/` and fails first unless `/data/data/applications.md` exists; `publish-volume-backup` (02:10, after the 02:00 etcd snapshot) copies the database with `VACUUM INTO` through `node:sqlite` in the publish image (claim mounted read-write, the WAL rule in `volume-backup.md`), checks `integrity_check`, fails on an empty `user` table (not `shares`: an account with its API key and no share is a normal state, and that guard failed every night until 2026-11-10), and uploads `volumes/career-ops/publish/`. The scripts contain no `${`.
- The Claude CLI can use the pooled CLIProxyAPI seats in place of the token (measured 2026-11-09: the web pod answered a one-word `claude -p` through the proxy in 1.9 s, `doctor.mjs` printed the gateway line, and the pod env held no `CLAUDE_CODE_OAUTH_TOKEN`). `anthropic_base_url` (`http://cliproxyapi.llms.svc.cluster.local:8317`, no `/v1` and no trailing slash) renders `ANTHROPIC_BASE_URL` into the HelmRelease env, and `anthropic_auth_token` renders `ANTHROPIC_AUTH_TOKEN` into `career-ops-secret`, which then has no `CLAUDE_CODE_OAUTH_TOKEN`. That token is the proxy's `api_key` or a key of its own; a value that differs from `cliproxyapi.api_key` is also rendered as a second entry in the proxy seed's `api-keys`, so the consoles show the dashboard's usage apart and the key survives a re-seed. The seed is copied once, so a running proxy takes a new key from the manager console first, and the token changes in `cluster.toml` only after that, or the dashboard's Claude calls answer 401. Claude Code reads both natively and sends the token as a bearer. The proxy's NetworkPolicy admits the web pod only when `anthropic_base_url` is set. The validator refuses the token together with the pair, and half the pair.
- The Claude OAuth token lasts one year. To renew it, run `claude setup-token` on the Mac, paste the output into `career_ops.claude_oauth_token` in `cluster.toml`, run `just configure` and push; reloader restarts the pod when the Secret changes.
