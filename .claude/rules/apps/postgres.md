# Postgres (`cnpg-system`, `[postgres.backup]`)

- `cnpg-system` holds the CloudNativePG operator (`cloudnative-pg`) and its backup plugin (`plugin-barman-cloud`). The plugin must run in the operator's namespace, and its TLS certificates come from cert-manager. The namespace enforces the `restricted` pod security level.
- `[postgres.backup]` in `cluster.toml` (endpoint, bucket and an access key pair, set all together or not at all) is the object store for Postgres backups. `components/postgres` renders only when it is set. An app with a database includes that component from its `app/kustomization.yaml`, which adds the `postgres-backup` ObjectStore and Secret and the `postgresql` ImageCatalog to the app's namespace, and its `ks.yaml` depends on `cloudnative-pg` and `plugin-barman-cloud` in `cnpg-system`. Backups land under the Cluster's name in the bucket, so Cluster names must be unique across namespaces. The component also adds a `postgres` PodMonitor that scrapes every instance in the namespace, and `cnpg-system/cloudnative-pg` holds the `postgres-backup` PrometheusRule: backup failed, backup older than 36 hours and WAL archiving failing, plus `PostgresBackupMetricMissing` (a cluster up with no backup metric for two hours, which is a broken PodMonitor or plugin; `radar-db` is left out, having no backup), the warning `PostgresReplicaLagging` (over 300 s for 15 minutes; every instance read 0 on 2026-10-31) and the warning `PostgresClusterDegraded` (under two instances up for 15 minutes; `ai-kb-db` is left out, having one). Its backup rules use the plugin's `barman_cloud_cloudnative_pg_io_*` metrics, because the `cnpg_collector_*` backup metrics stay at 0 with the plugin. The component's `postgres` CiliumNetworkPolicy admits the namespace on 5432, `cnpg-system`, the other instances and the `kube-apiserver` entity on 8000 (`kubectl cnpg status` arrives as that entity, which a NetworkPolicy cannot name, and one broke it on 2026-10-31), and `observability` on 9187, so a client in another namespace needs a new rule. Each ScheduledBackup sets `target: primary`, because on a quiet database a backup taken on a replica ended in a WAL segment that stayed unarchived for days, which no alert sees (read 2026-11-01). The `public` fixture sets the section.
- Each Cluster sets its own resources from its 7-day peak working set (read 2026-11-01, in a comment in `cluster.yaml.j2`): 50m CPU and 128Mi requested with a 512Mi limit on `ai-workspace-db`, `kener-db`, `matherlynet-db` and `reactive-resume-db`, 256Mi and 512Mi on `ai-kb-db`, `langfuse-db` and `pocket-id-db`, 256Mi and 768Mi on `radar-db`. All are Burstable, and a change to them rolls that one cluster.
- Every two-instance cluster sets `primaryUpdateMethod: switchover`, because a restart in place refuses new connections for up to the 180 s smart shutdown. The `kener-db` restart in place took 2 min 44 s; with the switchover, `matherlynet-db` and `reactive-resume-db` took about 34 s from the replica's roll to the old primary back up (both measured 2026-11-01). `ai-kb-db` has one instance, so it restarts in place. The same clusters set `podAntiAffinityType` to `required` when more than one node is not a control plane, and `preferred` otherwise, because instance pods do not tolerate the control plane taint; `public.toml` has one worker, so no fixture renders `required`.
- The shared image in `components/postgres/imagecatalog.yaml.j2` is pinned by digest, and that pin rolls every cluster at once, so `!ghcr.io/cloudnative-pg/postgresql` keeps it out of the tier 1 digest automerge in `.renovaterc.json5`. Its digest PR waits for a hand merge in a window; the merge on 2026-11-02 rolled all eight in under two minutes, the seven pairs by switchover, with no restarts.
- A plugin-barman-cloud version change also rolls every backed-up cluster, because the chart sets the sidecar image. On 2026-11-11 the catalog digest and plugin-barman-cloud 0.9.0 went out in one push, so the nine clusters rolled once, in about 3.5 minutes, and the one-instance `ai-kb-db` was down for under a minute (AI KB's connection errors stopped at 17:30:27 UTC).
