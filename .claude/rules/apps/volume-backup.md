# Volume backups (`[volume_backup]`)

- `[volume_backup]` in `cluster.toml` (a bucket and an S3 key pair, set all together, needing `[postgres.backup]`, whose endpoint it uses) gates a `volume-backup` CronJob in `pegaprox` (01:30 UTC), `network-optimizer` (01:40) and `rustfs` (06:10, after AI KB's 05:30 database backup, and only with `ai_kb_rustfs`). Each uploads `volumes/<namespace>/<namespace>-<timestamp>.tar.gz` and prunes objects older than 7 days, only after a good upload. The validator refuses a bucket or access key shared with `postgres.backup` or `etcd_backup`, because Network Optimizer's tar holds usable credentials; R2 tokens scope to a bucket, not a prefix, so all three namespaces can read all three tars. All three jobs together add about 68 MiB a night (first run 2026-11-02: Network Optimizer 62, PegaProx 4.7, AI KB 1.5), and R2's free 10 GB is the limit the operator set, with Postgres at about 3.1 GB and etcd at about 1.6 GB, so read the bucket sizes before adding anything else to R2.
- The two database jobs mount the app's claim read-write and run in the app's own pinned image, which must keep its tools: an init container makes the copy with `VACUUM INTO`, checks `integrity_check` and tars the rest of the volume, then a separate `upload` container holds the R2 Secret and no claim. Read-write, because read-only opens of a WAL database fail once the app has stopped and removed its `-wal` and `-shm` files, `immutable=1` gave "database disk image is malformed" against a live writer, and a plain file copy of a live database failed `integrity_check` 3 times in 12 (measured 2026-11-02). A second pod on the same RWO claim is fine, and `local-path` schedules it onto the app's node, so WAL locking holds.
- Never use BusyBox `tar` here: it honours only the last `-C` and exits 0 having dropped the volume, which is why a `keinos/sqlite3` image was rejected (measured 2026-11-02). Each job lists its tar afterwards and fails unless the key files and the database are in it, because a restore without them returns health 200 and cannot read its stored secrets. They also fail on a database with no `clusters` (PegaProx) or no `UniFiConnectionSettings` (Network Optimizer, 0 rows on a fresh install), because an app that lost its volume starts empty and regenerates its keys, and with 7-day retention the good tars would otherwise age out behind it; failing in the init container never reaches the prune. PegaProx without `.pegaprox_aes256.key` generates a new one and starts normally (measured). GNU `tar` exits 1 when a file changed as it read, which the jobs accept; 2 fails them. The member name of the database copy has no `./`, because `--exclude='./x*'` would also match a `-C /work .` form.
- PegaProx's job opens databases through `pegaprox.core.dbcrypto.connect`, because `db_key` may be base64 or hex, and skips a missing `syslog.db`, because `connect` would create it. The tar holds the field-encryption keys and not `db_key`, so a tar alone cannot be read, and restoring one needs `db_key` from `cluster.toml`. Neither `.pegaprox.key` nor `.pegaprox_aes256.key` equals `db_key` (compared live 2026-11-02). Network Optimizer's tar leaves out the GeoLite2 databases, `ieee-oui-cache.txt` and `temp/`, holds `.credential_key` by the operator's choice and is a plain restorable volume, so treat the bucket as secret; `NO_CREDENTIAL_KEY_FILE` could move that key out later. A second site's `sites/*.db` would be copied live, as the job's `shortcut:` comment says.
- AI KB's job mirrors `ai-kb-files` to scratch with the RustFS root pair in an init container and tars it, so `upload` holds only the R2 token, and it keeps history a live mirror would not; above about 1 GB a mirror fits better. An empty bucket passes. `langfuse-events` is left out, because ClickHouse has no backup and the events alone restore little. Object metadata is not preserved. Job pods carry no `app.kubernetes.io/name` label, so the apps' NetworkPolicies do not select them. The scripts contain no `${`; `flux envsubst --strict` leaves `$?` and `"$@"` alone (measured).
- A failed run fires `KubeJobFailed`, which stays firing until the failed Job is deleted. A CronJob that never runs fires nothing, and `etcd-snapshot` has the same gap. `private/scripts/restore-rehearsal.sh` proves a real tar restores, with `--network none` because a restored app acts on the real Proxmox and UniFi; for PegaProx it decrypts every stored secret. The restore steps are in `private/disaster-recovery.md`, and the `public` fixture sets the section.
