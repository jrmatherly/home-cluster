# It's a Plan (`[itsaplan]`)

- `[itsaplan]` in `cluster.toml` (`enabled`, needing `[postgres.backup]` and `[rustfs]`; the vault item `itsaplan` holds `BETTER_AUTH_SECRET`, `APP_ENCRYPTION_KEY`, `RUSTFS_ACCESS_KEY` and `RUSTFS_SECRET_KEY`) gates the `itsaplan` namespace, which enforces the `restricted` pod security level. `itsaplan/itsaplan` is It's a Plan, an issue tracker and project board with AI agents as members, from Jason's fork `jrmatherly/itsaplan` of `croffasia/itsaplan` since 1.13.0 (chart `oci://ghcr.io/jrmatherly/charts/itsaplan` and images `ghcr.io/jrmatherly/itsaplan-*`; never take upstream's tags, whose same-numbered releases differ; pinned by `OCIRepository` tag; the chart version is the release and its `appVersion` the image tag) at `plan.${SECRET_DOMAIN}` on the internal gateway, with no gateway `SecurityPolicy`, because the app has its own login (email and password, passkeys). The first account registered becomes the instance admin (the "god" role); Jason registered it on 2026-11-06, then configured a Pocket ID client in god mode (`/god/auth-provider`; the callback is `<API_URL>/api/auth/oauth2/callback/oidc`, so `https://plan.${SECRET_DOMAIN}/api/api/auth/oauth2/callback/oidc`) and turned email and password off under `/god/authentication`, so Pocket ID and passkeys are the only ways in. The provider settings live in the database, not in the HelmRelease. God mode has no link in the 1.10.0 UI; `/god` is typed by hand. The app's private-address guard did not block discovery against `auth.${SECRET_DOMAIN}` (measured 2026-11-06). It is a PoC as of 2026-11-06.
- The api lives under `/api` on the web's host, which the chart's own Ingress cannot do but the HTTPRoute can: the `/api` prefix is rewritten to `/` (`URLRewrite`, `ReplacePrefixMatch`) on the way to `itsaplan-api:3000`, the `/.well-known/oauth-authorization-server`, `oauth-protected-resource` and `openid-configuration` prefixes reach the api unrewritten for MCP clients' OAuth discovery, and everything else goes to `itsaplan-web:3001`. With one hostname the session cookie is `__Host-better-auth.session_token` with no Domain, so no other app on the domain receives it; a second hostname would set it on `.${SECRET_DOMAIN}`. The public auth path is therefore `/api/api/auth/...` (measured in Docker through Caddy, 2026-11-06).
- The chart's three images (api, web, worker; the Telegram bot is off) set no `USER`, and run as uid 1001 on a read-only root with every capability dropped (measured in Docker, 2026-11-06). The web needs a writable `/app/apps/web/.next/cache` for its image cache, which the chart mounts as an emptyDir since 1.13.1 (a `postRenderers` patch added it before); without it every optimized image logs an unhandledRejection. The api's `migrate` init container applies the migrations on every start and, before an upgrade with pending migrations, dumps the database to `/backups` first; the chart mounts an emptyDir there, so the dump would succeed and die with the pod, and `SKIP_PRE_MIGRATION_BACKUP` is exactly `"1"` because the CloudNativePG cluster is the backup (a fresh install never dumps, so a missing or read-only `/backups` only shows on the first upgrade, measured in Docker). The probe's database was Postgres 17 and a code search found no `CREATE EXTENSION` in the migrations (2026-11-06); the first rollout on the catalog's Postgres 18 under the `app` role proves it.
- Its stores: the CloudNativePG cluster `itsaplan-db` (two instances, WAL archiving and a daily backup at 06:00 UTC; the chart's `externalDatabase.url` is filled through `valuesFrom` from the `uri` key of the generated `itsaplan-db-app` Secret, so no database password is in the vault or in Git; the inline `externalDatabase.url` placeholder only lets flate render the chart offline, because a `targetPath` entry overwrites inline values, see `.claude/rules/flux-apps.md`) and the RustFS bucket `itsaplan-attachments` (the `rustfs_consumers` entry `itsaplan`; the namespace carries `rustfs.storage/client`, and its Kustomization depends on `rustfs-provision`). The other four secrets reach the chart's own Secret through `valuesFrom` from `itsaplan-secret`, which an ExternalSecret builds as a whole `values.yaml` document, because Flux splits a `targetPath` value on commas. Telemetry is off on the api and the worker (`api.env.TELEMETRY_DISABLED` feeds the shared ConfigMap and `worker.env.DO_NOT_TRACK` stays `"1"`; the fork's chart has no `worker.env.TELEMETRY_DISABLED`). Leave `api.env.PASSKEY_RP_ID` unset: the chart passes it since 1.13.0, and any value but the `APP_URL` host makes every registered passkey unusable. A NetworkPolicy admits the `network` namespace on 3000 and 3001, because the app reads the client address from `X-Forwarded-For`, and the app's own pods on 3000 (the web's server side and the worker call the api). Egress is not fenced; the app refuses outbound requests to private addresses on its own, with `SSRF_ALLOWED_HOSTS` for exceptions. Never change `APP_ENCRYPTION_KEY`: the stored provider keys become unreadable. The bucket has no volume backup yet.
- Two flags add to that. `itsaplan.web_push` turns on browser push: the vault item also holds `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY` (one pair from `bun run web-push:keys` in the app's repository; a new pair ends every browser subscription) and `WEB_PUSH_SUBJECT` (a `mailto:` or `https:` contact). The ExternalSecret's values document carries the private key under `secrets` and the other two under `api.env`, so the contact address stays out of Git; Flux deep-merges `valuesFrom` with the inline `api.env`. Push needs no route or egress change. `itsaplan.git_webhooks` (needs an ingress) adds a second HTTPRoute, `itsaplan-webhooks`, on `envoy-external` for the same hostname with one rule, `POST /webhooks/git/` to `itsaplan-api:3000` with no rewrite, and sets `GIT_WEBHOOK_BASE_URL` to the app's origin so the payload URL has no `/api` prefix. Every other path stays internal: public DNS comes from `cloudflare-dns`, which reads routes on `envoy-external`, and LAN DNS from `unifi-dns`, which reads routes on `envoy-internal`. The route has no SecurityPolicy, because a Git host sends no session and the api checks each delivery against the project's webhook secret (404 for an unknown id, 401 for a wrong signature, read from the app's source by the itsaplan session). The app sets no rate or size limit there, so a BackendTrafficPolicy on that route allows 10 requests a second per Envoy pod and bodies up to 5 MiB. A route-level policy replaces the gateway-level one, so this route has no compression or retry. The chart renders all four keys (measured with `helm template` on 1.13.1, 2026-11-23). Measured live 2026-11-23 at `8d057683`, against the external gateway's address: a POST to an unknown id answers 404 with the app's `Unknown webhook`, a GET of the same path, `/` and `/api/health` answer the gateway's empty 404, a 6 MiB body answers 413, and 40 parallel POSTs gave about 19 passes and the rest 429 (two Envoy pods at 10 a second each). Public DNS returns Cloudflare addresses and the console returns the internal gateway. `k8s_gateway` returns both gateways for the hostname, so a client that asks it instead of the console can land on the external gateway and get a 404 for the app.
- With `firecrawl_enabled`, `api.env.FIRECRAWL_ALLOWED_HOSTS` is `http://firecrawl-api.firecrawl.svc.cluster.local`, so the agents' Firecrawl tools can call the cluster's own instance (`.claude/rules/apps/firecrawl.md`). Fork release 1.15.0 added that key, which only the Firecrawl tools and the Firecrawl credential check read; up to 1.14.0 the same value sat in `SSRF_ALLOWED_HOSTS`, which is unset now. A chart before 1.15.0 drops the new key silently (its ConfigMap template renders named keys only), so the chart tag and the key move in one commit, and a rollback is a revert of `0fe34d6a`, which restores chart 1.14.0, the three images and `SSRF_ALLOWED_HOSTS` together. The rest of this bullet up to "Measured live at `0fe34d6a`" describes 1.14.0. Fork release 1.14.0 added the `http://host` form, which permits plain http to that exact host; a bare hostname stays https only. The entry has no port, because one with `:3002` matches nothing. The chart writes the value into the `itsaplan` ConfigMap that the api, web and worker Deployments all read (measured with `helm template` on 1.14.0, 2026-11-23). Every outbound path of the app that reads the list trusts that host in cleartext: project webhooks, attachment import by URL, git connections and agent endpoints, so a member who can import an attachment by URL can send a GET to Firecrawl's API. The credential is made in the app: Team settings, Integrations, Firecrawl, Instance URL `http://firecrawl-api.firecrawl.svc.cluster.local:3002`, API key empty. The app reaches that Firecrawl without TLS. 1.14.0 has no database migration, and its chart differs from 1.13.1 only in `Chart.yaml` (both reported by the It's a Plan session from `git diff v1.13.1 v1.14.0`), so a rollback is the chart tag and the three image tags back to 1.13.1 and the allow-list entry removed. Delete the Firecrawl credential first: 1.13.1 ignores its Instance URL and would send those calls to the Firecrawl cloud.
