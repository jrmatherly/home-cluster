# Observability (`[observability]`)

- `[observability]` in `cluster.toml` (a Grafana password, an InfluxDB password and an InfluxDB token, set all together or not at all) gates the whole `observability` namespace, which enforces the `privileged` pod security level for node-exporter. `kube-prometheus-stack` runs Prometheus, Alertmanager and Grafana, scrapes every ServiceMonitor, PodMonitor and rule in the cluster, and reaches etcd through the control-plane node addresses. The kube-state-metrics ServiceMonitor drops the `uid` label (`metricRelabelings` `labeldrop`), because FreeLens joins node metrics onto `kube_pod_info` by pod and namespace, and a pod recreated under the same name leaves two series differing only in `uid` until the old one goes stale, which fails the join. Ingress is limited by policy: Alertmanager admits the namespace and the `kube-apiserver` entity on 9093, Prometheus the namespace, `radar` and that entity on 9090, Grafana `network` and the namespace on 3000, and InfluxDB `network`, `network-optimizer` and the namespace on 8086, so a new caller in another namespace needs a rule (a NetworkPolicy cannot name the entity, hence the two Cilium policies). `influxdb` is InfluxDB 2 on the app-template chart, with org `home` and bucket `proxmox` created on the first start; that bucket is empty, because the Proxmox hosts write nothing there. Grafana and InfluxDB have routes on the internal gateway. Prometheus and Grafana have memory requests and limits set in the HelmRelease. Prometheus keeps `retention: 14d` with `retentionSize: 30GB`: its 20Gi claim is a `local-path` directory with no quota, so the cap is what stops it filling the node's `/var`, and it is about twice the 14-day footprint (blocks plus WAL 15.6 GB, 2026-10-31), so the time limit binds first. The cap applies through a config reload with no StatefulSet roll, and `--storage.tsdb.retention.size` still reads `0B`, so read `status/runtimeinfo`, which shows `2w or 30GiB` (measured 2026-10-31). `defaultRules.disabled` turns off `etcdHighNumberOfFailedGRPCRequests`, which counts every client-cancelled Watch as Unavailable (0.6 to 2.0 million per member per week, measured 2026-10-30) and fired as critical for six days; `etcdMembersDown` and `etcdHighFsyncDurations` stay on. The optional `proxmox_hosts` list (the Proxmox hosts' addresses, needing the other three) adds the `proxmox-hosts` ScrapeConfig, which scrapes node-exporter from Debian's `prometheus-node-exporter` package, installed by hand on each host, on port 9100, and the `proxmox-hosts` PrometheusRule, which alerts when `node_zfs_zpool_state` shows a pool not online (a REMOVED rpool mirror member froze cp-1's disk on 2026-10-12) or a host's exporter is down for 10 minutes, and a page needs `discord_webhook`; Cilium masquerades the scrape to the node's address, so a host firewall admits every node address on 9100, because any node may host Prometheus. The optional `discord_webhook` field, which needs the other three, gives Alertmanager a Discord receiver that reads the URL from the mounted `alertmanager-secret`; without it every alert goes to the `null` receiver. The optional `heartbeat_url`, which needs `discord_webhook`, routes the always-firing `Watchdog` alert to a `heartbeat` webhook receiver, reading the URL from the same Secret, so an outside service pages when the pings stop and a dead Prometheus, Alertmanager or node is noticed; without it `Watchdog` goes to `null`. The route sets `group_interval: 1m`, because that gives a ping every 6 minutes against 10 with the chart's 5m, where one missed ping would pass the check's 15-minute limit (measured on Alertmanager v0.34.2, 2026-10-31). The service here is Healthchecks.io, with period 10m and grace 5m. It answers an unknown URL with HTTP 200, so the first ping has to be read on its page. A 25-minute `Watchdog` silence paged email and Discord 15 minutes after the last ping, and the check went up 31 s after the silence ended (2026-10-31). The heartbeat cannot see a broken Discord webhook, because it is its own receiver. The steps are on the Grafana plugins page. The optional `grafana_oidc_client_id` and `grafana_oidc_client_secret` pair (an OIDC client created by hand in Pocket ID, needing `[pocket_id]`) adds a Pocket ID sign-in to Grafana next to the password form; only the Pocket ID group `cluster_admins` gets a role, as Grafana server admin, and everyone else is refused. The optional `grafana_secret_key` encrypts the data source secrets Grafana stores, replacing the built-in default that its advisor flags; never change it once set. The image ships its datasource plugins in a read-only directory, and Grafana's updater unloads a plugin before it fails to replace it there (this took the Prometheus and InfluxDB data sources down on 2026-10-06). So never list them in `[plugins] preinstall`; the HelmRelease sets the chart's `shadowBundledPlugins: true`, which hides that directory so Grafana's default preinstall list fetches them into the writable plugins directory on the volume, and `preinstall_auto_update: true` in `grafana.ini` keeps them current, because the chart turns it off otherwise. The experimental `pluginsAutoUpdate` feature toggle, with `plugins.update_strategy = minor`, also updates every non-core, unpinned, unprovisioned plugin between restarts, because the catalog publishes a bundled plugin's new version days after the Grafana release that carries it and the advisor flags the gap until then. Other Grafana plugins go in the chart's `plugins` list, which installs them before provisioning runs, and one table at the top of the HelmRelease template decides which are on. Infinity is always on, with one data source and no authentication. The `canvas` panel is in that table too: Grafana 13.3 loads it as a standalone plugin (`[plugin.canvas] as_external = true`) and the image ships it only in the bundled directory that `shadowBundledPlugins` hides, so without it every start logs "Core plugin expected to be loaded as external, but it is missing" and the visualization is absent from the picker (measured 2026-10-30; after the fix "Plugin registered" pluginId=canvas). Each of the GitHub and Sentry data sources ships a Grafana dashboard from `kube-prometheus-stack/app/dashboards/`, gated by the same fields: the GitHub one is the plugin's bundled "GitHub Default" with the edits listed in `.claude/skills/update-apps/references/apps.md`, and the Sentry one is hand-written, because the plugin bundles none, and both ConfigMaps carry `kustomize.toolkit.fluxcd.io/substitute: disabled`, because the JSON holds Grafana's own `${datasource}` expressions and Flux's post-build substitution fails on them. The optional `github_app_id`, `github_app_installation_id` and `github_app_private_key` (a GitHub App, set together; the key is the PEM file) add the GitHub data source, and the optional `sentry_org` and `sentry_token` pair (a Sentry internal integration, with `sentry_url` defaulting to `https://sentry.io`) adds the Sentry data source; the gitignored `private/grafana-plugins-setup.md` lists the steps. When `nvidia_enabled`, the `grafana-llm-app` ConfigMap provisions the LLM app through the chart's plugins sidecar, pointing it at LocalAI with the key from grafana-secret with both abstract models mapped to its model name, `qwen-3.5-4b`, and the namespace carries the `localai.ai/client` label. Its panel title and description buttons fit a LocalAI slot of 16384 tokens (llama-server's held 8192 from 2026-10-11 and 2048 before, when the dashboard description button got HTTP 400 on a dashboard whose JSON was over about 2000 tokens). The `public` fixture sets the section and every plugin field.
