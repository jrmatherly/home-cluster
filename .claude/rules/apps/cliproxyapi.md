# CLIProxyAPI and CPA-Manager-Plus (`[cliproxyapi]`)

- `[cliproxyapi]` in `cluster.toml` (a `management_key`, an `api_key` and a `manager_admin_key`, set all together, needing no other section) gates the `llms` namespace, which enforces the `restricted` pod security level. `llms/cliproxyapi` is CLIProxyAPI (`eceasy/cli-proxy-api`), an OpenAI-, Anthropic- and Gemini-compatible proxy that pools subscription logins (Claude, Codex and others) behind one client key, at `llms.${SECRET_DOMAIN}` on port 8317. `llms/cpa-manager` is its management UI, CPA-Manager-Plus (`ghcr.io/seakee/cpa-manager-plus`), at `llms-admin.${SECRET_DOMAIN}` on port 18317. Both are on app-template, on the internal gateway only, with no gateway `SecurityPolicy`: the manager's `CPA_MANAGER_ADMIN_KEY` is its only login, and clients send `api_key` as a bearer token. It is a PoC as of 2026-11-06.
- Git seeds the proxy's config once. `cliproxyapi-secret` holds a whole `config.yaml`, mounted read-only at `/seed`, and the `seed-config` init container copies it to `/data/config.yaml` only when that file is absent. The app rewrites the file at start (it replaces the plaintext `management.secret-key` with a bcrypt hash) and persists every management-API write to it, so a read-only file makes those writes answer 500 (measured in Docker, 2026-11-06). After the first start the manager UI owns the config, and a change to the seed in Git reaches a running instance only if the volume's copy is deleted. The manager keeps the plaintext management key in its own Secret and stores it encrypted with `/data/data.key`; losing that file makes the stored key unrecoverable.
- Measured in Docker on the pinned images (2026-11-06). Both images set no `USER`, and both run as uid 1000 on a read-only root with every capability dropped. The proxy writes only under `/data` (`config.yaml`, `auths/` with the OAuth token files and `kv.db`) and answers `/healthz` with no key (`/health` is 404). The image bakes `TZ=Asia/Shanghai`, so the HelmRelease sets `Etc/UTC`. The manager writes only to `/data` (`data.key`, `usage.sqlite` and its WAL, a lock file, `usage-imports/`), gets a `/tmp` emptyDir (it stayed empty, but was not proven unneeded), and answers `/health` with no key. Exactly one manager subscribes to a proxy's usage queue, so it runs one replica. Both Deployments use `Recreate`, and both volumes are 1Gi `local-path` claims with `forceRename` and `retain: true`, because each holds the only copy.
- `trusted-proxies` is the pod CIDR, because the gateway forwards the client address and the app bans an address after five bad management keys. `disable-control-panel: true` turns off the bundled panel, which the app would otherwise download from GitHub; `/management.html` is 404 on the proxy. `usage-statistics-enabled: true` feeds the manager's usage pages.
- Provider logins are added in the manager. It returns an authorization URL whose redirect is `http://localhost:54545/callback` (Claude) or `http://localhost:1455/auth/callback` (Codex). The browser lands on a failing localhost page, and the whole URL from the address bar is pasted into the manager's callback field.
- NetworkPolicies admit the `network` namespace on each app's port, and the proxy also admits the manager's pods on 8317. Egress is open: the proxy dials the providers, plus an antigravity version check and the Grok CLI version from npm at start and every 3 hours.
- Not done: no volume backup (the OAuth tokens and the manager's `data.key` exist only on the volumes), no metrics, no docs page, no provider API keys in `cluster.toml`. The gitignored `private/cliproxyapi-setup.md` lists the setup steps. The `public` fixture sets the section, and the invalid fixture `partial-cliproxyapi` covers its all-or-none check.
