# RustFS (`[rustfs]`)

- `[rustfs]` in `cluster.toml` (a root `access_key` of at least 16 letters and digits, a `secret_key` of at least 32, and `node`, a worker from `[[nodes]]` that is not a controller, set all together) gates the `rustfs` namespace, which enforces the `restricted` pod security level. `rustfs/rustfs` is RustFS, an S3-compatible object store for the cluster's own apps, from its chart (`rustfs` 1.0.4) through a classic `HelmRepository` at `https://charts.rustfs.com`, because upstream publishes no OCI chart. It runs standalone (one Deployment, one 20Gi `local-path` claim at `/data`, `nodeSelector` on `rustfs.node`), so every object lives on that node's disk only, with no parity: the server logs `storage_class_zero_redundancy`, a single node must stay on RustFS's default `strict` durability, and replication to R2 is impossible because R2 has no bucket versioning. The image is `ghcr.io/rustfs/rustfs` pinned by digest; the chart passes `podSecurityContext` through, so seccomp goes in values and no postRenderers patch is needed. The web console is off, logs go to stdout (`obs_log_directory: ""`, which also drops the chart's logs claim), the ingress is off, and `scanner.cycle_secs` is 21600 because single-disk memory grows with the scanner's sweep rate (rustfs/rustfs#8121). There is no Prometheus endpoint (metrics are OTLP push only), so nothing scrapes it. Clients use `http://rustfs-svc.rustfs.svc.cluster.local:9000`, path style, region `us-east-1`; a NetworkPolicy admits port 9000 from the namespace itself and from namespaces labelled `rustfs.storage/client: "true"`, and denies all egress. Each consumer is an entry in the computed `rustfs_consumers` (name, bucket and a key pair from the app's own section). The `rustfs-provision` Flux Kustomization `dependsOn` `rustfs` (which sets `wait: true`) and runs the `rustfs-provision` Job: `rc` from `docker.io/rustfs/rc` as uid 65534, reading the root pair from `rustfs-secret` and the consumer pairs from `rustfs-provision-secret`, waits up to five minutes for `/health/ready`, then for each consumer runs `rc bucket create --ignore-existing` and creates a service account with an inline policy scoped to the bucket, or updates the secret and policy of one that exists, so a rerun converges (measured against the pinned images in Docker on 2026-10-18: first run creates, second converges, a rotated secret replaces the old one, and the key gets AccessDenied on any other bucket). The Job's pod template carries `rustfs_consumers_checksum`, its script is a `configMapGenerator` ConfigMap whose hashed name is in the pod template, and the Job carries `kustomize.toolkit.fluxcd.io/force: enabled`, so a changed consumer or an edited script recreates the immutable Job and it runs again; its Kustomization sets `wait: true`, so a failed run shows as not ready. The server Deployment gets a Reloader annotation through a `postRenderers` patch, so a changed root pair restarts it. The script contains no `${`, because Flux post-build substitution would rewrite it. It sends the stdout of `rc admin service-account create` and `update` to /dev/null, because `rc` prints the new secret key on success and it landed in the Job log (measured 2026-10-18). The `public` fixture sets the section, and the invalid fixtures `partial-rustfs`, `rustfs-bad-node`, `rustfs-short-secret` and `rustfs-duplicate-key` cover its checks; the validator refuses a consumer access key that equals the root key or another consumer's, because each pair is a separate account.
